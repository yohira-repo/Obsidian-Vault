# 固定IP 簡易Webサーバ公開 検討

作成：2026-09-15 ／ リモートVPNとは別件。固定IP `124.100.212.73`（map-e固定IP1・全ポート可）でWebサーバを全世界公開する際の検討。

## 0. 前提（2026-09-15 ユーザー確定）

| 項目 | 内容 |
|---|---|
| 用途 | **Web**サーバ |
| 公開範囲 | **全世界公開** |
| 設置場所 | **社内DMZ**（新設セグメント） |
| データ機微度 | **社外秘なし・トレーニング用** |
| 位置づけ | 現行方針「インバウンド公開なし」([[00_サマリ]]5章) に**1穴だけ開ける**部分転換。VPNとは独立作業 |

> 機微データなし＝万一侵害されても情報漏えい面のダメージは小さいが、**踏み台化・横展開**のリスクは残る。よって「**内部から隔離**」を最優先に設計する。

---

## 1. 配置：DMZセグメント新設

- **新VLAN40（DMZ）案**：`192.168.208.0/24`（GW `.1`＝RTX1300）／VID **40**（既存10/20/30/保守200/VPN201と重複なし。VID1は使わない＝罠③）
- サーバIPは固定 `192.168.208.10` 等（`.2`〜`.99` 内）
- コアスイッチ XS508TM の**空きポート（Port7/8/SFP+）**にDMZをタグVLANで割当、またはRTX1300 `lan flexible-port` で分離（罠⑧：RTX1300はvlan port mapping不可）
- **原則**：
  - `DMZ → 内部（VLAN10/20/保守/VPN/AWS）` = **全拒否**（侵害時の横展開遮断）
  - `内部 → DMZ` = 保守に必要な最小限のみ（例：管理は保守セグメントからのみ）
  - `インターネット → DMZ` = 公開ポートのみ許可（下記3）
  - `DMZ → インターネット` = 証明書更新・OSパッチのため**アウトバウンドは許可**（できれば宛先/ポート限定）

## 2. サーバ本体

- **リバースプロキシ構成**（nginx / Caddy）でアプリを直接晒さない。Caddyは証明書自動化が楽
- **コンテナ/使い捨て前提**（Docker等）で復旧を容易に。トレーニング用なら再構築も軽い
- OSは最小構成、不要サービス停止

## 3. 公開（NAT・フィルタ）

### 静的NAT（map-e固定IP1宛 → DMZサーバ）
```
# nat descriptor masquerade static で 443/80 をDMZサーバへ転送
# ※map-e配下のNAT記述・評価順序はVPN(§11)同様の注意。実機検証項目
nat descriptor masquerade static 1 <n> 192.168.208.10 tcp 443
nat descriptor masquerade static 1 <n> 192.168.208.10 tcp 80   # 80はHTTPS恒久リダイレクト用途に限定
```
- **開放は 443 のみを基本**、80はリダイレクト専用。**管理ポート(22/3389)は絶対に公開しない**（保守/VPN経由のみ）
- 既存の「着信拒否」フィルタに**この1穴だけ**を開ける。穴の管理を台帳化

### フィルタの型（既存 §9 の構造を踏襲）
- インターネット→DMZ：**443（＋80）のみ静的pass**、他はreject
- DMZ→内部：**明示reject**（`ip filter reject 192.168.208.0/24 → 128/64/192/200/201/10.0.0.0/16`）
- DMZ→インターネット：pass（できれば443/80/DNS/NTP等に限定）

## 4. セキュリティ（全世界公開の肝）

- [ ] **TLS証明書**：Let's Encrypt自動更新（DMZ→ACME/443アウトバウンド確保）
- [ ] **管理面の非公開**：SSH/RDPは外部非公開。管理は保守セグメント or VPN経由
- [ ] **ブルートフォース/DoS**：fail2ban・レート制限（map-e固定IPは狙われやすい）
- [ ] **パッチ運用**：OS/nginx/アプリの更新頻度と手順を事前に決定
- [ ] **ログ・外形監視**：アクセスログ＋死活監視。異常検知の通報先
- [ ] **バックアップ**：構成をコード化（Compose/IaC）し再構築を担保
- [ ] **WAF**（任意）：Cloudflare等を前段に置くと、**オリジンIP秘匿＋DDoS緩和**。全世界公開なら特に有効（→ 6章の代替案とも関連）

## 5. DNS・ドメイン

- 独自ドメイン/サブドメインの**Aレコードを `124.100.212.73`** へ
- **回線変更でグローバルIPが変わると再設定が必要** → 運用メモに明記（過去に 153.156.71.228→124.100.212.73 の変更実績あり）
- メールサーバは**立てない**（SPF/逆引き/レピュテーション運用が重く、機微用途でもないため不要）

## 6. 代替案の比較（先に検討する価値あり）

| 案 | 内容 | 向き |
|---|---|---|
| **A：社内DMZに自前公開**（本命） | RTX配下にDMZ VLAN40 | 学習・自由度重視。運用は自社負担 |
| B：Cloudflare Tunnel等 | オリジンを公開せずトンネルで出す | **インバウンド穴を開けずに公開**でき安全。固定IPすら不要 |
| C：AWS側で公開 | 既にWeb公開環境はAWS移行済 | 機微なし学習用なら**AWSに置く方が隔離・運用が楽**な可能性 |

> トレーニング用途なら **B（Cloudflare Tunnel）** は「社内に着信穴を開けない」点で有力。**目的が『DMZ公開そのものの学習』ならA**。→ 用途の主目的（学習対象がサーバ運用か、ネットワーク公開設計か）で選ぶ。

## 7. 既存構成との整合・運用

- **リモートVPN(L2TP)と同一固定IPでインバウンド共存** → ポート衝突なし（VPN=500/4500/1701、Web=443/80）だがフィルタ適用順序を確認
- **UPS空き口**の確認（サーバ＋周辺機器）
- **撤去手順**（NAT/フィルタの穴を塞ぐ）を最初に用意
- 一時公開なら**期限を決めて閉じる**運用

---

## 8. 先に決めたい点（次の一手）

1. **代替案 A/B/C の選択**（学習の主目的しだい。B=Cloudflare Tunnelは着信穴なしで安全）
2. Aの場合：DMZの**VLAN ID/セグメント**（案：VID40・`192.168.208.0/24`）で確定してよいか
3. 公開ドメインの有無（Aレコード先）

→ 決まれば、Aなら DMZ VLAN・NAT・フィルタの**config当たり**を [[config_RTX1300]] へ追補する形で具体化する。
