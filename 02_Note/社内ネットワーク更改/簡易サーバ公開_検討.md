# 固定IP 簡易Webサーバ公開 検討

作成：2026-09-15 ／ リモートVPNとは別件。固定IP `124.100.212.73`（map-e固定IP1・全ポート可）で、**K8s/OpenStack ベアメタル勉強会用のDMZ環境**を新設し全世界公開する際の検討（DMZ公開そのものの学習が主目的）。

## 0. 前提（2026-09-15 ユーザー確定）

| 項目 | 内容 |
|---|---|
| 採用案 | **案A：社内DMZに自前公開**（＝「DMZ公開そのものの学習」が主目的） |
| 用途 | **勉強会**：オリジナルの **K8s／OpenStack 環境（ベアメタル）** を構築し公開。定期開催 |
| 公開範囲 | **全世界公開**（公開設計の学習が目的） |
| 設置場所 | **社内DMZ**（新設）。既存環境をなるべく触らず、**RTX1300 の LAN1 物理ポートを利用**したい |
| 機材 | **余っているミニPC（複数台）** を流用（ベアメタルはAWSでは試しづらい／コスト高のため社内で） |
| データ機微度 | **社外秘なし・トレーニング用** |
| 時期 | **今すぐではない**（切替・VPN安定後）。定期公開＝**勉強会のたびに開閉**する運用 |

> **なぜAWSでなくオンプレか**：ベアメタルK8s／OpenStack（物理ノード・ネットワーク層の学習）はAWSでは再現しづらくコストもかかる。余剰ミニPCがある。→ 社内DMZが最適。
>
> **リスク認識**：公開K8s/OpenStackは**攻撃対象になりやすい**（管理API・ダッシュボード・多数のポート）。機微データは無くても**踏み台化・横展開・採掘マルウェア**の標的になりうる。よって「**内部から完全隔離＋公開は勉強会時のみ＋終了後に閉じる**」を大原則にする。

## 1. 配置：LAN1を丸ごとDMZに転用（2026-09-15 確定）

> **前提決定**：**保守セグメントは廃止**（実質未使用。RTX/XS508TM/BE9400の管理はVLAN10経由、HGWは一時直結で保守セグメントを使っていない）。RTXの非常時アクセスは**シリアルコンソール**を最終手段とする。

### 方式：LAN1（8ポートL2スイッチ）をそのままDMZインターフェースに
- **`ip lan1 address` を `192.168.200.1/24` → `192.168.208.1/24` に変更するだけ**。`lan flexible-port` は使わない。
- **メリット**：
  - **RTX再起動が不要**（flexible-portを使わないため。アドレス変更・フィルタ追加は再起動なしで反映）。
  - **ミニPCはLAN1の8ポートに直挿し**（最大8ノード）＝**別途DMZスイッチ不要**。9ノード以上に増えたら後日スイッチ追加。
  - LAN3のタグVLAN幹線・コアスイッチ XS508TM には一切触れない。
- 廃止に伴う整理（実装時）：保守関連のフィルタ（`2039`/`2002`/`2010`/`2102`/dynamic`3010`/`3011`）と **DHCP scope 40（`192.168.200.x`）** を撤去/読み替え。

### アドレス・接続
- **DMZサブネット：`192.168.208.0/24`（GW `.1`＝RTX1300 lan1）**。既存（10=128/20=64/30=192/VPN=201）と重複なし。
- ミニPC群は `192.168.208.10`〜 に配置（LAN1ポートへ直挿し）。
- K8s/OpenStackが内部で使うオーバーレイ/追加セグメントはDMZ内で完結させる（RTX側へ漏らさない）。

### フィルタ原則（片方向許可＝既存VLAN10→VLAN20と同じ型・罠⑤⑥）
- **`VLAN10/20 → DMZ` = 許可（TCP全般＝案i）**。参加者が自席PCからラボ（K8s/OpenStack）を操作するため。lan1 の `out` に静的pass＋dynamic（戻り許可）、`in` に内部宛reject。
- **`DMZ → 内部（VLAN10/20/VPN/AWS）` = 全拒否**（侵害時の横展開遮断＝DMZの肝）。
- `インターネット → DMZ` = 公開ポートのみ許可（下記3。**勉強会時のみ開け、終了後に閉じる**）。
- `DMZ → インターネット` = イメージpull・パッチ・証明書のため**アウトバウンドは許可**（できれば宛先/ポート限定）。
- VLAN30（ゲスト）→DMZ は拒否のまま。

## 2. サーバ本体

- **リバースプロキシ構成**（nginx / Caddy）でアプリを直接晒さない。Caddyは証明書自動化が楽
- **コンテナ/使い捨て前提**（Docker等）で復旧を容易に。トレーニング用なら再構築も軽い
- OSは最小構成、不要サービス停止

## 3. 公開（NAT・フィルタ）

### 静的NAT（map-e固定IP1宛 → DMZサーバ）
```
# nat descriptor masquerade static で 443/80 をDMZサーバへ転送
# ※map-e配下のNAT記述・評価順序はVPN(§11)同様の注意。実機検証項目
nat descriptor masquerade static 1 <n> 192.168.208.10 tcp 443
nat descriptor masquerade static 1 <n> 192.168.208.10 tcp 80   # 80はHTTPS恒久リダイレクト用途に限定
```
- 公開ポートは**勉強会の演習内容に応じて開ける**（Web演習なら443等）。**管理ポート(SSH22等)はインターネットに公開しない**＝管理・操作は**VLAN10/20（内部）から**行う。
- 既存の「着信拒否」フィルタに**必要な穴だけ**を開け、**勉強会終了後に閉じる**。開けた穴を台帳化。

### フィルタの型（既存 §9 の構造を踏襲）
- インターネット→DMZ：**443（＋80）のみ静的pass**、他はreject
- DMZ→内部：**明示reject**（`ip filter reject 192.168.208.0/24 → 128/64/192/200/201/10.0.0.0/16`）
- DMZ→インターネット：pass（できれば443/80/DNS/NTP等に限定）

## 4. セキュリティ（全世界公開の肝）

- [ ] **TLS証明書**：Let's Encrypt自動更新（DMZ→ACME/443アウトバウンド確保）
- [ ] **管理面の非公開**：SSH/RDPは**インターネット非公開**。管理・操作は**VLAN10/20（内部）から**（片方向許可で到達）
- [ ] **ブルートフォース/DoS**：fail2ban・レート制限（map-e固定IPは狙われやすい）
- [ ] **パッチ運用**：OS/nginx/アプリの更新頻度と手順を事前に決定
- [ ] **ログ・外形監視**：アクセスログ＋死活監視。異常検知の通報先
- [ ] **バックアップ**：構成をコード化（Compose/IaC）し再構築を担保
- [ ] **WAF**（任意）：Cloudflare等を前段に置くと、**オリジンIP秘匿＋DDoS緩和**。全世界公開なら特に有効（→ 6章の代替案とも関連）

## 6. 代替案の比較（先に検討する価値あり）

| 案                    | 内容               | 向き                               |
| -------------------- | ---------------- | -------------------------------- |
| **A：社内DMZに自前公開**（本命） | RTX配下にDMZ VLAN40 | 学習・自由度重視。運用は自社負担                 |
| B：Cloudflare Tunnel等 | オリジンを公開せずトンネルで出す | **インバウンド穴を開けずに公開**でき安全。固定IPすら不要  |
| C：AWS側で公開            | 既にWeb公開環境はAWS移行済 | 機微なし学習用なら**AWSに置く方が隔離・運用が楽**な可能性 |

> **【2026-09-15 決定：案A採用】** 目的が「**DMZ公開そのものの学習**」であり、ベアメタルK8s/OpenStackはAWSでは試しづらくコスト高、かつ余剰ミニPCがあるため、**社内DMZ自前公開（案A）**を採用。B/Cは今回見送り（Bは「穴を開けない」ため学習目的に合わない、Cはベアメタル学習に不向き）。

## 7. 既存構成との整合・運用

- **リモートVPN(L2TP)と同一固定IPでインバウンド共存** → ポート衝突なし（VPN=500/4500/1701、Web=443/80）だがフィルタ適用順序を確認
- **UPS空き口**の確認（サーバ＋周辺機器）
- **撤去手順**（NAT/フィルタの穴を塞ぐ）を最初に用意
- 一時公開なら**期限を決めて閉じる**運用

- 案A（社内DMZ自前公開）。用途＝K8s/OpenStack ベアメタル勉強会（定期）、余剰ミニPC流用。
