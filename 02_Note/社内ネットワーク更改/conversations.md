## 2026-08-18（追記）　IPv6アドレス配布方式の訂正：PD方式 → RA方式

### 訂正内容
当初「ひかり電話契約がある場合にHGWがDHCPv6-PDを取得し競合する可能性」と記載したが、これは**フレッツ光ネクスト(1G)のルール**で誤りだった。正しい整理は以下。

| 回線 | 条件 | ルータで選ぶ方式 |
|---|---|---|
| 光クロス(10G) | 原則（ひかり電話の有無に関わらず） | DHCPv6-PD |
| **光クロス(10G)** | **XG-100NE配下にIPoEルータを設置する場合** | **RA方式（例外）** |
| 光ネクスト(1G) | ひかり電話あり＋HGW使用 | RA方式 |
| 光ネクスト(1G) | ひかり電話なし | RA方式 |

「常にPD」の主語は**回線から見て1台目の機器＝XG-100NE**。PDを受けるのはHGWであり、HGWは受け取ったプレフィックスを配下へ再委任せず、LAN側へ /64 を1本RAで広告するだけ。よって**HGW配下のRTX1300はRA方式でしか設定できない**。

```text
NTT網 ──(DHCPv6-PD /60)──▶ XG-100NE ──(RA で /64 を1本広告)──▶ RTX1300
                            ▲                                   ▲
                    PDを受け取るのはHGW                  RA方式で設定（PD不可）
```

### 誤ってPD方式にした場合の症状（最重要）
プレフィックスを正しく取得できずMAPルールが適用されないため、**IPv6は通信できるがIPv4が一切通らない**。「IPv6は通るので回線は生きている」と誤認しやすく、開通当日の切り分けが難航する典型パターン。

### 確定した設計事項
- **RTX1300のIPv6取得方式は RA方式**
- **社内LAN（VLAN 1〜3）はIPv4のみ**。RA方式ではプレフィックスを切り出せないため、社内へIPv6は配布しない。IPv6はHGW–RTX1300間のWAN区間で、IPv4 over IPv6トンネルの外側としてのみ使用
- インターネット接続は固定グローバルIPv4 1個によるNAPT（従来のPPPoE運用と同等）
- **DNSはパブリックDNSを直接指定**（RA方式時、DNS自動設定が `dhcp lan2` となりHGWをDNSサーバとして参照するが到達経路が自動生成されず、IPv6名前解決に失敗する既知事象の回避）
- 固定IPサービスでは、ひかり電話契約の有無に関わらず `ONU – XG-100NE – ルータ` が**必須構成**。HGWを外した回線直結は不可（＝HGW前提で設計するのが正解）
- Setup Guide の「IPv6取得方式：DHCPv6-PD方式を選択」は本構成では誤りだが、参考資料のため無修正。**方式選択は他資料の記載（RA方式）を優先**する旨を明記した

### 残る要確認事項（絞り込み後）

|---|---|---|
| HGW側の必要設定 | 固定IP1利用時にXG-100NE側へ必要な設定（接続先設定の扱い・DMZ要否） | OCN / NTT東日本 |
| VPNの通過性 | MAP-E上でAWS VGW向けIKE(UDP500/4500)・ESPが通過するか | OCN / 社内検証 |

### 確定した値

### アクセス制御方針（確定）
| 通信方向 | 可否 | 備考 |
|---|:--:|---|
| VLAN 1 → VLAN 2 | 許可 | 動的フィルタによる片方向許可 |
| VLAN 2 → VLAN 1 | 拒否 | 例外なし |
| VLAN 3 → VLAN 1・2 | 拒否 | ゲスト分離 |
| VLAN 3 → インターネット | 許可 | ゲストはインターネットのみ |
| VLAN 1 → AWS VPC(10.0.3.0/24) | 許可 | 業務系のみ |
| VLAN 2・3 → AWS VPC | 拒否 | 開発系・ゲストからは接続しない |
| 保守セグメント → VLAN 1・2 | 許可 | 保守作業用（逆方向は拒否） |

### 技術的な結論：片方向許可の実装方式
「VLAN1→VLAN2 のみ許可」は RTX1300 の **動的フィルタ（`ip filter dynamic`）** で実現する。

- 許可対象は**セッションを開始する方向**であり、VLAN1発のセッションの**戻りパケットは自動的に許可**される（ステートフル動作）
- **静的フィルタ（`ip filter`）だけで実装すると戻りパケットも落ちて通信不能**になる。これは実装時の典型的な失敗パターンなので注意

### 設計上のトレードオフ（合意済み）
プリンターをVLAN1（`192.168.128.20`）に置き、VLAN2→VLAN1を例外なく拒否するため、**VLAN2（開発メンバ席・Develop-WiFi）からは印刷できない**。印刷はクライアント→プリンター方向にセッションを張るため拒否対象になる。

- 「VLAN2からの印刷は不要」という運用方針で確定
- 将来必要になった場合は、`192.168.128.20` の印刷ポート（TCP 9100／631／515）のみを静的フィルタで例外許可する追加設計を行う（資料に明記済み）
- 同様に、AWSへの通信はVLAN1のみのため、開発用途でAWS接続が必要になった場合は方針見直しが必要（資料に明記済み）

## 2026-08-18（追記5）　VLAN2は紙媒体を一切扱わない

### 方針
**VLAN 2 は紙媒体を直接・間接に利用しない**。したがって複合機（`192.168.128.20`）とVLAN 2 の間の通信は、印刷・スキャンとも**双方向で一切不要**。

### アクセス制御への反映
| 通信 | 可否 | 実装 |
|---|:--:|---|
| VLAN2 → 複合機（印刷・管理画面・スキャンボックス取得） | 拒否 | VLAN2→VLAN1の拒否で自動的に遮断。**例外許可は設けない** |
| 複合機 → VLAN2（スキャンのSMB/FTP送信） | **拒否** | VLAN1→VLAN2は原則許可のため通ってしまう。**送信元 192.168.128.20 からVLAN2宛を静的フィルタで明示拒否**し、動的フィルタの許可より前段に配置する |

### 副次的なメリット
複合機の通信範囲がVLAN 1 内（＋必要な外部通信）に限定される。複合機はファームウェア更新頻度が低く踏み台になりやすい機器のため、防御上も有効。

### 実装順序の注意
RTX1300のフィルタは**適用順序が結果を決める**。「複合機発VLAN2宛の静的拒否」を「VLAN1→VLAN2の動的許可」より**前**に置かないと、拒否が効かない。

## 2026-08-18（追記6）　リモートアクセスVPN（L2TP/IPsec）のユーザー別切り分け

### 質問：ユーザーによりVLAN1／VLAN2に切り分けできるか
**結論：可能。ただし「VLANに入れる」のではなく「払い出しIPで切り分ける」方式になる。**

L2TP/IPsecクライアントはRTX1300の `pp anonymous` インターフェースに終端され、VLANインターフェースには所属しない。また **anonymous pp は1つしか作成できない**ため、ユーザーごとに別VLANへ収容することは不可能。代わりに、ユーザーごとに固定IPを払い出し、送信元IPレンジでフィルタを分岐させて同等の制御を実現する。

### 確定した設計
主用途は**社外から自席PCへのリモートデスクトップ／SSH接続**。

| 区分 | 払い出しレンジ | 到達範囲 | 許可ポート |
|---|---|---|---|
| 業務ユーザー | 192.168.201.16/28（.17〜.30） | VLAN1 192.168.128.0/24 のみ | TCP 3389 / 22 |
| 開発ユーザー | 192.168.201.32/28（.33〜.46） | VLAN2 192.168.64.0/24 のみ | TCP 3389 / 22 |

- **VPN専用セグメント 192.168.201.0/24 を新設**（VLAN1の予備範囲から取らない）。理由：VPN経由の通信をログ・監査で即判別でき、開発系の分離もサブネット単位で1行記述できる。
- **/28 のサブネット境界に揃える**ことでフィルタが簡潔になる（各区分14ユーザーまで）。
- 業務ユーザーはAWS・VLAN2・VLAN3・複合機・保守セグメントへ到達不可。開発ユーザーはVLAN1・AWS・VLAN3・保守セグメントへ到達不可。
- Linux端末があるため **SSH(TCP 22) も許可**（RDP 3389 と合わせて2ポートのみ）。

### コマンド要点
- ユーザー別固定IP：`pp auth username <ユーザー> <パスワード> 192.168.201.17`（第3引数でIP指定）
- **固定指定IPは `ip pp remote address pool` と重複させないこと**（重複するとプールから別アドレスが払い出されフィルタが効かない）。本設計では全ユーザー固定指定・プール未使用とする。
- 同時接続数はバインドするトンネル数に依存（`pp bind tunnel1-tunnelN`）

### 発見した前提条件：RDP先PCのIP安定化が必須
接続先が自席PCのため、**DHCPでIPが変動するとRDP／SSHの宛先を指定できない**。対処としてRTX1300のDHCP予約を採用。

- `dhcp scope bind 1 192.168.128.101 <MACアドレス>`
- PC側は「自動取得」のままで端末設定の変更は不要
- これに合わせ**DHCP範囲を細分**：`.100`〜`.149`=予約（RDP/SSH対象PC）、`.150`〜`.199`=自動払い出し
- **MACアドレス台帳の作成が必要**（PC名・利用者・MAC・予約IP）

### 切替前に確認が必要な点
- Windowsファイアウォールのリモートデスクトップ受信規則が「ローカルサブネットのみ」になっていると、別セグメント（192.168.201.x）からの接続が拒否される
- Linux端末の sshd / firewalld / ufw で 192.168.201.0/24 の許可が必要
- RTX1300のL2TP/IPsec同時接続数の上限（機種仕様、要確認）

#### 本設計の方針（変更なし）

## 2026-08-19（追記15）　VLAN間フィルタの確定（動的フィルタ仕様の検証結果）

唯一残っていた技術的未確定事項（動的フィルタの方向・評価順）について、ヤマハ公式仕様と公式設定例を確認し**確定版に仕上げた**。

### 確認できた仕様（3点）
| # | 仕様 | 設計への意味 |
|---:|---|---|
| 1 | 動的フィルタは最初から存在せず、**トリガとなるコネクション検出時に生成**される。**最初のパケットには静的フィルタが適用**される | **転送方向の静的フィルタに `pass` が必須**。ここで reject するとセッションが生成されず通信できない |
| 2 | 動的フィルタを `secure filter out` に指定すると、**戻りパケットは `in` 側の静的 reject に関わらず通過**する | 公式例は `in` を `reject * *` にしても戻り通信が成立 |
| 3 | 動的フィルタのプロトコルに **ICMP は指定できない** | **VLAN間の ping は通らない**。疎通確認はTCPで行う |

### 採用した構成の型
**宛先側インターフェース（lan3/2＝VLAN20）の `in` で相手発を拒否し、`out` に静的 `pass` ＋ `dynamic` を置く。**
ヤマハ公式設定例「ローカルルーターで複数のLANを接続（片方向の通信）」と同一構造。

重要な副次的結論として、**VLAN10・VLAN30側のインターフェースには `secure filter out` を設定しない**こととした。`out` に静的 reject を置くと、インターネットやVLAN20からの戻りパケットまで落ちるため。制御は各IFの `in` と lan3/2 の `out` に集約する。

### ICMPの扱い
案A（pingを使わず、疎通確認はTCPで実施）を採用。案B（ICMPを双方向許可）は運用が楽だがVLAN20からVLAN10へのホスト存在調査が可能になり分離が緩むため不採用。

### 反映内容
- [[config_RTX1300]] 9章を全面差し替え：9-2 動作原理（公式仕様＋パケットフロー図）／9-3 フィルタ定義 確定版／9-4 適用 確定版／9-5 ICMPの扱い（案A・B比較）／9-6 投入後の確認7項目。「要検証」表記を撤回
- [[社内LANネットワーク設定]]：実装上の注意に構成の型、LAN側 `out` を設定しない理由、ICMP非対応を追記
- [[切替・障害切り分け手順]]：疎通確認8をTCPベース（`Test-NetConnection -Port 3389`）に変更、5-6 を症状6パターンに拡充

### まず結論：VLAN10は「アンタグ（ネイティブ）」で統一
このAPのUIは「Untagged VLAN」を使う方式なので、VLAN10をネイティブ（アンタグ）にするのが素直（AP・スイッチ双方すっきり、フラット→VLAN移行も滑らか）。
- AP：Untagged VLAN = 10、Management VLAN = 10（SSID Office=10 / Develop=20 / Guest=30）
- XS508TM Port5：VLAN10 = アンタグ(U)、VLAN20/30 = タグ(T)、PVID10

### この画面（BE9400 LAN/IP）の設定 — ★ただし“最後”に
先にSSIDを3つ仕上げてから（Office=10／Develop=20／Guest=30）、最後にLAN/IPを変更：
- DHCP Client：Disable
- IP Address：`192.168.128.3`
- Subnet Mask：`255.255.255.0`
- Gateway：`192.168.128.1`
- Primary/Secondary DNS：`8.8.8.8` / `8.8.4.4`
- 802.1Q VLAN：Untagged VLAN：☑ `10`／Management VLAN：`10`
- Apply
→ Apply後、APは `192.168.128.3`（VLAN10）へ移り、`192.168.0.x` のPCからは切れる（正常）。**PCを `192.168.128.50/24` にして** `https://192.168.128.3/` で再接続。

### SSIDの残り
- Office-WiFi → VLAN 10、Guest-WiFi → VLAN 30（Guestは Advanced 内の Wireless/Client Isolation を有効）
- Develop-WiFi（VLAN20）はそのまま。6GHzは任意。

### 次（XS508TM）で合わせる
- Port5：VLAN10＝アンタグ(U)＋PVID10、VLAN20/30＝タグ(T)
- [[config_XS508TM]] §7 のロックアウト回避順で構築 → VLAN10アクセスポートのPCは **DHCP自動取得** で本番確認（`ping 8.8.8.8`／各SSIDのVLAN確認）
