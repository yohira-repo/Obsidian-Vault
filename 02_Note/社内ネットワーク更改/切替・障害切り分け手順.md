# 光クロス切替・障害切り分け手順

本資料は**切替当日に手元で開いて使う実施手順書**です。上から順に実施し、異常が出たら「5. 障害切り分け」へ飛んでください。

設計の根拠は [[社内LANネットワーク設定]]、機器構成は [[ネットワーク構築提案書]]、進行管理は [[インターネット回線更改]] を参照してください。

> **最重要**：異常時にまず疑うのは **RTX1300のIPv6取得方式**です。HGW配下では **RA方式**が正しく、DHCPv6-PD方式にすると「IPv6は通るがIPv4が一切通らない」状態になります（→ 5-1）。

## 3. 切替手順

### 3-1. 物理接続

| # | 作業 | 確認ポイント |
|---:|---|---|
| 1 | XG-100NE を設置し、光ケーブル・電源を接続 | 前面ランプが正常表示になること |
| 2 | 保守用端末を XG-100NE のLANポートへ**一時直結**し、管理画面 `http://192.168.1.1/` にアクセス | DHCPで `192.168.1.x` を取得できること |
| 3 | XG-100NE の **Wi-Fi（2.4GHz／5GHz）をOFF** | SSIDの発信が停止すること |
| 4 | XG-100NE の**ルータ接続先設定は投入しない**（パススルー運用） | 設定済みなら削除 |
| 5 | 保守用端末のケーブルを撤去 | 常設経路は設けない |
| 6 | **XG-100NE LAN4 → RTX1300 LAN2 RJ-45**（CAT6A） | LAN1〜3は未使用 |
| 7 | **RTX1300 LAN3 RJ-45 → XS508TM Port 1**（CAT6A） | タグVLAN 10・20・30 |
| 8 | 保守用端末 → **RTX1300 LAN1 ポート1** | 保守セグメント `192.168.200.0/24` |
| 9 | XS508TM Port 2〜6 の結線（開発／総務／営業・管理／PoEエクステンダー／複合機） | [[社内LANネットワーク設定]] のポート割当に従う |

### 3-2. RTX1300 設定投入（この順序で実施）

| # | 設定内容 | 注意 |
|---:|---|---|
| 1 | **IPv6：RA方式**で設定 | **PD方式にしないこと**（→ 5-1） |
| 2 | OCNバーチャルコネクト（固定IP1）：固定IP／Tunnel Destination／インターフェースID | RAで受けた /64 と組み合わせてWAN側IPv6を生成 |
| 3 | **DNS：パブリックDNSを直接指定** | 自動設定の `dhcp lan2` は使わない（→ 5-2） |
| 4 | VLAN 10・20・30 のインターフェース／DHCPスコープ | GWは各 `.1`、DHCPは `.100`〜`.199` |
| 5 | **DHCP予約**（`dhcp scope bind`）：RDP/SSH対象PC | `.100`〜`.149` の範囲から |
| 6 | フィルタ（**適用順序が重要**） | ①複合機→VLAN20の静的拒否 → ②VLAN10→VLAN20の動的許可 → ③その他 |
| 7 | 保守セグメント（LAN1 = `192.168.200.1/24`） | 保守→業務の片方向 |
| 8 | L2TP/IPsec（ユーザー別固定IP、トンネル数分バインド） | プールは使用しない |
| 9 | AWS VGW 向け IPsec（`10.0.3.0/24`、VLAN10のみ） | BGP／Dual Tunnel |

> 各段階を投入したら、次に進む前に「4. 段階的疎通確認」の該当ステップを実施してください。まとめて投入すると切り分けが困難になります。

## 5. 障害切り分け

### 5-1.【最頻・最優先】IPv6は通るがIPv4が通らない

| 項目 | 内容 |
|---|---|
| **症状** | `ping6` は通る／IPv6サイトは見えるが、`ping 8.8.8.8` が通らずIPv4通信が全滅 |
| **原因** | RTX1300のIPv6取得方式が **DHCPv6-PD** になっている。HGW配下ではプレフィックスを正しく取得できず、**MAPルールが適用されない**ためトンネルが成立しない |
| **確認** | `show status ipv6 dhcp`（PD取得の失敗有無）／`show ipv6 address`（LAN2のアドレス）／`show status tunnel 1` |
| **対処** | **RA方式へ変更**し、トンネルを再確立 |

> 「IPv6は通るので回線は生きている」と誤認しやすいのが最大の罠です。**IPv4が通らない場合はまずここを見る**こと。

### 5-2. IPv4は通るがIPv6の名前解決ができない

| 項目 | 内容 |
|---|---|
| **症状** | IPv4通信は正常だが、IPv6での名前解決が失敗する |
| **原因** | DNS設定が自動で `dhcp lan2` となりHGWをDNSサーバとして参照するが、そのサーバへの到達経路が自動生成されない（既知事象） |
| **対処** | **パブリックDNSを直接指定**、または静的経路を追加 |

### 5-3. まったく通信できない

上から順に確認します。

1. XG-100NE の前面ランプ（光回線・認証の状態）
2. ケーブルの結線先（**XG-100NE は LAN4**、**RTX1300 は LAN2**）とカテゴリ（CAT6A）
3. `show status lan2` でリンクアップ・速度
4. **XG-100NE に接続先設定が入っていないか**（入っていると二重ルータになる）
5. XG-100NE を再起動 → 5分待って再確認
6. RTX1300 を再起動
7. NTT東日本 故障受付（`0120-594-202`）へ

### 5-4. グローバルIPが契約の固定IPと違う

- 原因：XG-100NE 側でIPv4を終端している／RTX1300のトンネル設定の投入漏れ
- 確認：外部IP確認サイト、`show nat descriptor address`、`show config` でトンネル設定
- 対処：XG-100NE の接続先設定を削除、RTX1300のトンネル設定を再投入

### 5-5. 特定のVLANだけ通信できない

- RTX1300 LAN3 のタグVLAN設定（VLAN 10・20・30すべて収容されているか）
- XS508TM Port 1 がタグポートになっているか
- XS508TM の下位ポート（Port 2〜6）が正しいアンタグVLANになっているか
- LXW-10G8 はアンマネージドのため設定不要（=疑う対象外）

### 5-6. VLAN間の制御が意図通りに動かない

| 症状 | 原因 | 対処 |
|---|---|---|
| VLAN10→VLAN20 が通らない | 静的フィルタのみで実装しており**戻りパケットが落ちている** | **動的フィルタ（`ip filter dynamic`）**で実装する |
| VLAN20→VLAN10 が通ってしまう | フィルタの適用順序が誤っている | 拒否ルールを許可ルールより**前**に配置 |
| 複合機からVLAN20へ通信できてしまう | VLAN10→VLAN20の許可に含まれてしまっている | 送信元 `192.168.128.20` のVLAN20宛拒否を、動的許可より**前**に配置 |

### 5-7. リモートアクセスVPNの不具合

| 症状 | 確認・対処 |
|---|---|
| VPNは接続できるが社内に届かない | `ip pp secure filter in` の内容。到達先VLANのTCP 3389／22が許可されているか |
| 払い出しIPが指定値と違う | `pp auth username` の指定IPが `ip pp remote address pool` の範囲と**重複していないか**（重複するとプールから払い出される） |
| 複数ユーザーが同時接続できない | バインドしているトンネル数が不足（`pp bind tunnel1-tunnelN`） |
| RDPだけ繋がらない（pingは通る） | **Windowsファイアウォール**のRDP受信規則が「ローカルサブネットのみ」になっている |
| SSHだけ繋がらない | Linux端末の `sshd` / firewalld / ufw で `192.168.201.0/24` が許可されていない |

### 5-8. AWS拠点間VPNが確立しない

- `show ipsec sa` で Phase1／Phase2 の状態を確認
- MAP-E（IPv4 over IPv6）上で **IKE（UDP 500／4500）・ESP** が通過するか（OCNへの要確認事項）
- 固定IP1は1アドレス専有のため通る想定だが、NGの場合はOCNへ問い合わせ

## 7. 切り戻し手順（So-net回線へ退避）

### 判断基準

- 予定した作業時間内にIPv4疎通が確立しない
- 原因の切り分けがつかず、業務再開時刻に間に合わない見込み

上記に該当したら**切り戻しを優先**します。復旧を粘るより業務再開を優先してください。

### 方式

So-net回線は代替回線として従来から運用しており、**切り替え実績のある手順**です。RTX1300側の設定変更や退避用configは不要です。

1. 総務・営業系のLANケーブルを So-netルータ側へ差し替える
2. 総務・営業系のPCを再起動する
3. プリンターのIPアドレス切替(192.168.0.20)
4. 無線APのIPアドレスを変更(192.168.0.*)
5. 外部への疎通を確認し、社内へ周知
6. 翌営業日以降、原因を切り分けて再挑戦の日程を調整

### 新構成で追加される影響

従来の切り替えとの違いとして、新構成で追加した以下の機能は切り戻し中は停止します。

- **リモートアクセスVPN（L2TP/IPsec）／AWS拠点間VPN** — リモート勤務者・AWS連携が停止するため、切り戻し判断時に考慮が必要
- **VLAN分離とVLAN間フィルタ** — フラットな1セグメントに戻る
- **固定IP機器** — 複合機 `192.168.128.20`、XS508TM `.2`、WBE710 `.3` はSo-netルータのセグメントと異なるため到達できない
