# リモートアクセスVPN（L2TP/IPsec）投入手順

作成：2026-09-15 ／ 段階3（実機投入）の作業手順。設計の本体は [[config_RTX1300]] §10、全体像は [[00_サマリ]] 7章を参照。

> **位置づけ**：切替当日ではなく、インターネット/VLAN/AWS拠点間VPNが安定稼働した後の**別作業**（優先度低）。既存の通信（VLAN・AWS-VPN）へ影響を与えないよう、追加投入のみで構成する。

## 0. 前提・確定事項（2026-09-15時点）

- **map-e固定IP1はインバウンド全ポート利用可**（段階1で確定）。L2TP着信（UDP500/4500/1701・ESP）は通る。
- **到達先は2系統**（2026-09-15）：業務4アカウント（`yohira`/`t.kido`/`mogik`/`iizukak`、払出 `.17`〜`.20`）＝**VLAN10到達**、開発2アカウント（`yohiradev`/`t.kidodev`、払出 `.33`/`.34`）＝**VLAN20到達**。※業務アカウント名はメールローカル部（`XXX@alphacmc.co.jp`）、開発は`＋dev`。開発アカウントは当面暫定・運用で増減。
- トンネル合計5本（同時接続の目安 VLAN10=2／VLAN20=3）。到達先はトンネルでなくアカウント払出IP＋フィルタで決まる（解釈A）。
- グローバルIP：`124.100.212.73`（map-e固定IP1）。
- **本手順の最重要検証ポイント** → [3. local address のmap-e対応](#3-最重要-ipsec-ike-local-address-の切り分け)

## 2. 投入順序（段階的・各段階で確認）

> まとめて投入すると切り分け不能になるため、**最小構成→1アカウント確認→全展開**の順で進める。

### ステップA：L2TP/IPsec 最小構成（1トンネル＋1アカウント）
1. [[config_RTX1300]] §10 の **IPsec基本＋tunnel1000＋`pp anonymous`（`yohira`のみ）＋フィルタ4010/4011/4099** を投入。
2. この時点では `tunnel1000` の1本のみ有効化。
3. `save`。

### ステップB：外部から1アカウントで接続テスト（→ 3章の切り分け）
1. 外部回線端末に **`yohira`** でL2TP/IPsec接続。
2. 接続成立を確認：`show status l2tp` ／ `show ipsec sa` ／ syslog（`l2tp syslog on`）。
3. 払出IP `192.168.201.17` を受領しているか、クライアント側で確認。
4. VLAN10のPCへ **RDP(3389)／SSH(22)** で接続確認（**pingは通らない**＝仕様。TCPで確認）。

### ステップC：全展開
1. 残りアカウント（業務 `t.kido`/`mogik`/`iizukak`、開発 `yohiradev`/`t.kidodev`）を `pp auth username` に追加。開発用フィルタ `4020`/`4021` と `ip pp secure filter in` への追加も行う（VLAN20側戻りは §9 lan3/2 out で対応済み）。
2. トンネルを5本（`tunnel1000`〜`tunnel1004`）へ拡張（`ipsec transport`・`ipsec tunnel`番号を重複させない）。
3. `pp bind tunnel1000-tunnel1004` を確認。
4. `save`。
5. 複数ユーザーでの同時接続と、各自の接続先PCへのRDP/SSHを確認。

## 3. 【最重要】`ipsec ike local address` の切り分け

**map-e配下では固定IP直書きが `send:0` で不成立になる**実績が §11（AWS拠点間VPN）にある。L2TP（応答側・`remote address any`）でも同様かを**ステップBで最初に確定**する。

| 試行順 | 設定 | 判定 |
|---:|---|---|
| 第1候補 | `ipsec ike local address 1 192.168.128.1`（LAN IP）＋ `ipsec ike local name 1 124.100.212.73 ipv4-addr` | §11で成立した方式。まずこれで試す |
| 第2候補 | `ipsec ike local address 1 124.100.212.73`（固定IP直書き） | 第1がNGなら試す |

- 切り分け材料：syslog の IKE フェーズ1/2 の成否、`show ipsec sa`、着信パケットの有無。
- **応答側特有の注意**：L2TPはRTXが待ち受け側。map-eのポート専有（全ポート可）が効いていれば UDP500/4500 の着信がRTXへ届く。届かない場合はHGWパススルー／map-e状態（`show status tunnel 1` のmap-e）を疑う。
- 確定した方式を [[config_RTX1300]] §10 の該当行へ反映（要検証注記を解消）。

## 4. 接続確認チェックリスト

- [ ] 外部からL2TP/IPsec接続成立（`show status l2tp`／`show ipsec sa`）
- [ ] 払出IPが設計どおり（`yohira`=.17 等）
- [ ] VLAN10のPCへ RDP(3389) 成功
- [ ] VLAN10のPCへ SSH(22) 成功
- [ ] **業務アカウントはVLAN20へ到達しないこと**（`192.168.64.x` の3389/22へ接続不可）
- [ ] **開発アカウント（yohiradev/t.kidodev）はVLAN20へ到達すること**（`192.168.64.x` の3389/22へ接続可）／**かつVLAN10へは到達しないこと**
- [ ] 同時接続（複数アカウント）で相互干渉なし
- [ ] 既存通信（VLAN間・インターネット・AWS拠点間VPN）に影響が出ていないこと

## 5. 切り戻し（問題時）

- 追加投入のみのため、**投入した §10 部分を `no` で除去**すれば元の状態に戻る（`tunnel1000`〜、`pp anonymous`、フィルタ`4010/4011/4099`、`ipsec transport`）。
- 迷う場合は事前退避した `show config` を復元。
- **リモートVPNは既存の業務通信と独立**しているため、切り戻しても VLAN・インターネット・AWS-VPN には影響しない。

## 6. 投入後の残确認（端末側）

- Windowsファイアウォールのリモートデスクトップ受信規則が `192.168.201.0/24` を許可しているか（各対象PC）。
- Linux端末の sshd／firewalld が `192.168.201.0/24` を許可しているか。
- VPN利用者へ**接続先グローバルIP `124.100.212.73`** を周知。
