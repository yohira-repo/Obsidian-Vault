### CC/転送漏れ対策の議論

**提案**: Google Workspace管理コンソールのルーティング／コンプライアンスルールで、条件付き自動BCCをかける（人の記憶に依存しない）。

**ユーザーの反応**: 管理権限はあるが、営業担当の全メールに機械的にBCCをかけるのは適切か疑問。「条件付き」とは具体的にどんな条件が設定できるのか、という質問。

**回答（要点）**:

- Google Workspaceのルーティングルールは、**組織部門（OU）単位**でルールの適用対象を絞れる（例: 営業担当・営業事務総務担当のOUのみに適用し、他部門には影響させない）。
- **宛先/送信元のドメインリスト**で条件を絞れる（既知の顧客・協力会社ドメインのみを対象にし、無関係な外部ドメイン宛のメールは対象外にできる）。
- 件名・本文のキーワードでの絞り込みも可能だが、キーワード運用自体が新たなルールになるため優先度は低い。
- ヘッダーの存在チェックで「すでにバーチャルメールがCC/Toに入っている場合は対象外にする」といった重複防止条件も設定可能。

**推奨する落とし所**: 機械的BCCルールは「既存顧客・既存協力会社との定常的なやりとり」（ドメインが既知）だけに適用する保険として使う。まだドメインが未登録の新規開拓中のやりとりは、機械的なルールでは拾えないため、運用ルール（CC徹底）に頼る。これは「契約成立で新規→既存に切り替わる」という前段の整理とも整合する。

**要検証（実装フェーズで確認すべき事項）**: Google Workspace管理コンソールの実際の条件設定UI・オプションの詳細（バージョンにより変わるため、実際のコンソールで確認が必要）。

### 重要な訂正: バーチャルメールボックス自体はGmail管理ではない

**ユーザーの指摘**: 「バーチャルメールボックス自体だけを取り込めばよい」という前提が誤り。**バーチャルメールアドレスはGmailで管理されているものではない**（＝実体を持つGmailメールボックスではなく、転送のためのアドレス/エイリアスに過ぎない）。

**判断**: Gmail APIで直接接続できる対象は「バーチャルメールアドレスの転送先」であり、バーチャルメールアドレス自体ではない。転送先が単一の共有メールボックス（Googleグループ/共同トレイ等）なのか、対象ロールの各メンバー個人のGmailに個別に転送されているのかを確認する必要がある。この確認待ち。

**回答**: 対象ロールの各メンバーの**個人Gmailにそれぞれ個別に届く**（一人一タブ、fan-out方式）。

**問題**: 個人Gmailに直接アクセス（ドメイン全体委任）するのは、以下の理由で望ましくない。

- 個人の受信箱全体を覗く形になり、プライバシー・ガバナンス上のコストが高い
- 同じメールが複数人に届くため、複数の個人メールボックスから同じメールを取り込むと**重複（デデュープ）処理**が必要になる

**解決案**: バーチャルメールの転送先に、個人Gmailとは別に**専用の共有取り込み用メールボックス（Googleグループの共同トレイ、または共有メールボックス）を新設**し、そこを唯一のGmail API接続先とする。

- 前段で議論した「OU＋既知ドメイン条件での自動BCCルール」の宛先を、この専用共有メールボックスに向ける（個人宛の従来フローとは並行して動く別経路として追加する）
- これにより、個人メールボックスへのアクセスは一切不要になり、重複処理の問題も発生しない（取り込み元が単一になるため）
- 既存の「バーチャルメール→各個人へfan-out」という現状の運用フローは変更せず、そのままにしておける（実務への影響が小さい）

**現在のステータス**: この解決案をユーザーに提示し、承認待ち。

**ユーザーの反応**: 同じ発想だったため合意（OK）。追加質問: 「専用共有メールボックス」には専用アカウントが必要か？

**回答（要点）**:

- **選択肢1: Googleグループの共同トレイ（Collaborative Inbox）** — 追加ライセンス費用は不要。ただし、Gmail API（`users.messages`/`watch`によるPub/Subリアルタイム通知）をそのまま使えず、別のAPI体系になる可能性があり、案A（Gmail API + Pub/Sub）との整合性が崩れうる。
- **選択肢2: 実在の人物に紐づかない専用のGoogle Workspaceユーザーアカウント** — 通常のGmailメールボックスとして扱えるため、案Aの方式（Gmail API + Pub/Sub）がそのまま使える。ただし一般的に追加のユーザーアカウント＝追加ライセンス費用が必要になる可能性がある（正確な要否・費用はWorkspaceの契約内容次第で、要確認）。

### 新しい視点: GMOレンタルサーバのメールアドレスを取り込み先にする

**ユーザーからの共有**: 自社のメールサーバは**GMOのレンタルサーバ**。社員分はGmailに連携（転送）させているが、協力会社向けなど必要な場合はメールサーバから直接受信することもある。**GMOのレンタルサーバ側は、メールアドレスをほぼ無限に作成できる**（Google Workspaceのライセンス制約を受けない）。この特性を使い、取り込み先をGoogle Workspace側ではなくGMOのレンタルサーバ側に作れないか、という提案。ユーザー確認: 「Gmail案の利点はBCCに条件付きで共有メールアドレスを入れ込めることだったはず」。

**判断**: これは非常に筋が良い。整理すると以下の構造になる。

- **メールの発生元（送受信そのもの）**: 営業担当／営業事務総務担当の個人Gmail（Google Workspace）。ここは変更しない。
- **自動BCCルール（OU＋既知ドメイン条件）**: これはGoogle Workspace管理コンソールの機能。**BCC先として指定するアドレスは、Workspace内部のアカウントである必要はなく、外部の任意のメールアドレスを指定できる**（一般的に、外部のメール監査/アーカイブサービスへBCCする用途で使われる機能のため、外部ドメイン指定が可能なのは自然）。
- **取り込み専用メールボックス（アーカイブ先）**: これを**GMOのレンタルサーバ上に作成**すれば、Google Workspaceのライセンス問題が完全になくなる。GMOのレンタルサーバは通常IMAPアクセスに対応しているはずなので、Track1システムはそこへIMAPポーリング（5〜15分間隔、既に合意済みの方式）で取り込む。

**結論**: Gmail（Google Workspace）が必要なのは「メールの発生源」としての役割のみ。**「取り込み・保管先」は、Google Workspaceである必要がなく、GMOのレンタルサーバ上の新規メールアドレスにできる**。これでGoogle Workspaceの追加ライセンス／Archived User／エイリアスといった論点はすべて不要になる可能性が高い。

**要検証（実装フェーズ）**:

1. Google Workspaceの自動BCCルール（コンプライアンスルール）が、外部（Workspace外）ドメイン宛のBCC指定に対応しているか（一般的には対応しているはずだが、実際の管理コンソールで確認）
2. GMOのレンタルサーバの契約プランが、プログラムからのIMAPアクセスに対応しているか（プランにより異なる可能性があるため確認）

### GMO⇄Gmailの連携方式の実態（重要な前提の追加）

**ユーザーからの共有**: 現状、外部からのメールはまず**GMOのレンタルサーバが自社ドメイン（alphacmc.co.jp）でMXとして受信**し、そこから `xxxxx@alphacmc.co.jp.test-google-a.com` という特殊なアドレスに**サーバー側で転送**することで、Google Workspace（Gmail）に着地させている。この方式は移行時に代理店から提案されたもので、詳細はユーザー自身も把握していない。

**判断（技術的な解釈）**: `<独自ドメイン>.test-google-a.com` は、**MXレコードをまだGoogleに向けずに、Google Workspace移行時の「並行配信（デュアルデリバリー）」を行うためのGoogle公式の既知の手法**。つまり、今回のケースでは特殊なハックというより一般的な移行パターンの延長線上にある。ただし、この構成には次のような実務上の含意がある。

- **MXの実体（外部から見た受信の窓口）は依然としてGMOのレンタルサーバ**。つまり、外部の顧客・協力会社から届く受信メールは、Google Workspaceに至る前に、必ずいったんGMOのレンタルサーバを経由している。
- これにより、**受信メールの取り込みについては、Google Workspaceのコンプライアンスルールを経由せず、GMOのレンタルサーバの段階で直接コピー/転送する**という、さらに単純な代替経路が理論上存在する。
- 一方、**送信メール（営業担当からの返信）はGMOを経由せず直接Gmailから送信される**ため、送信側の取り込みには従来通りGoogle Workspace側の自動BCCルール（またはCC徹底の運用ルール）が必要になる点は変わらない。
- ダブルホップ転送（GMO→test-google-a.com→Workspace）の過程で、SPF/DKIM等のヘッダー情報や添付ファイルがどこまで保持されるか、Workspaceのコンプライアンスルールがこの転送後のメールに正しく発火するか、といった点は**未検証**。代理店が設定した経緯があるため、詳細は代理店または社内のシステム管理者に確認する必要がある。

**現在のステータス**: この論点はメール基盤の実装詳細に深く入り込んでおり、外部（代理店/管理者）への確認が必須な項目が複数出てきた。ここで深掘りを一段落させ、決定事項と要検証事項を整理して設計書に落とし込む方向へ進める。

### 送信経路も実は未確定（追加の不確定要素）

**ユーザーからの共有**: 「営業担当の送信はGmailから直接」という前提は、実は**現在問い合わせ中**。過去にGmailを使わずOutlookを使用していたメンバーがいたため、送信経路が全員Gmail一本化されているとは限らない。

**判断**: 送信経路（Gmail直送のみか、一部Outlook等の別クライアント／別SMTP経由もあるか）も未確定要素として扱う。もしOutlook等がGMOのSMTPを経由して送信している場合、送信メールの一部もGMOレンタルサーバ側を通る可能性があり、受信側と同様にGMO側での捕捉が選択肢になり得る。ただし現時点では推測であり、確認結果を待つ。

**現在のステータス**: メール基盤に関する未確定・要確認事項が複数（Workspace外部BCCの動作、GMOのIMAP対応、ダブルホップでのヘッダー保持、送信経路の実態）出てきた。これらは社内確認・代理店確認が必要で、この場（brainstorming）でこれ以上詰めるのは非効率。**「決定事項」と「要確認事項」を切り分けて設計書に落とし込む**方向へ移る。
