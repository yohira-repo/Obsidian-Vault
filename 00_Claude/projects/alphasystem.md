## 2026-07-27 タスク0(MFクラウドAPI連携基盤)の設計確定とロードマップ改訂

- **経緯**: API提供状況の調査結果を受けて方針を確定し、タスク0の詳細設計を行った。あわせて元資料に「経費管理」が追記されたため、ロードマップに反映した。
- **確定した前提**:
  - 会計は**クラウド会計(通常版)**を利用中。会計Plusではないため、公開APIで自己申請ベースで着手できる。
  - 仕入側(タスク3)の連携先は**クラウド債務支払 API**とする(クラウドインボイス[受領] APIではない)。
  - 給与連携は公開APIがないため、**CSV連携の自動化**で進める。
  - シークレット管理は **AWS Secrets Manager(Client ID/Secret・暗号化キー)+ alphadb(access/refresh token を暗号化保存)** の組み合わせとする。alphaexapi は現状 Secrets Manager 未使用のため新規導入となる。
- **ロードマップ改訂**: 元資料への「経費管理」追記を受け、タスクを 0=基盤 / 1=顧客連動 / 2=売上請求 / 3=仕入請求 / **4=経費管理(新規)** / 5=給与 に改訂。経費は公開APIがありOAuth基盤に乗るため、CSV方式となる給与より先に着手する。
  - これにより「OAuth基盤(タスク0)が会計・請求書・債務支払・経費の4製品を賄い、給与のみ別方式」という切り分けが明確になり、基盤に投資する価値が高まった。
- **タスク0の設計方針**(詳細は [design/2026-07-27-task0-mf-api-foundation-spec.md](design/2026-07-27-task0-mf-api-foundation-spec.md)):
  - **連携コードの置き場所は alphaexapi に集約**。理由: OAuth Authorization Code Grant はHTTPSのリダイレクトURIが必須でHTTPサーバを持つ alphaexapi しか受けられない。またトークンのリフレッシュを1箇所に集約しないと同時更新で refresh token が競合する。既存の google-drive の「provider + 用途別モジュール」二層構成に合わせる。
  - **MF側の外部IDは汎用マッピングテーブル`MfLink`1本で保持**。理由: 製品ごとに個別アプリ登録が必要なため顧客1件が製品ごとに別IDを持ち、業務テーブルにIDカラムを持たせるとエンティティ×製品でカラムが増殖する。1テーブルに寄せると既存スキーマを変更せずに済み、`syncStatus`/`syncedAt`で現状の入り繰りを追跡できる。
  - トークンは `MfOauthToken` テーブルに製品単位(`unique(mfProduct)`)で保持。ECS複数タスクでの並行リフレッシュは行ロックで直列化する。
  - 請求書APIの1秒3回制限に対応するため、共通クライアントに製品別スロットルと429の指数バックオフリトライを持たせる。
- **次のアクション**: タスク0の実装計画(plan)を作成する。未確定事項として、MFサンドボックス環境の有無、HTTPS必須のリダイレクトURIのローカル開発時の扱い、ECSタスク定義へのシークレット注入経路の確認が残る。

## 2026-07-27 MFクラウド経費APIの調査結果とタスク0設計の修正

- **経緯**: タスク4(経費管理)で「社員・プロジェクト別の原価データ」が実際にAPIで取得できるかを、公開OpenAPI仕様(Swagger)の実物で検証した。
- **タスク4の実現可能性: 確認済み**。経費明細(`ExTransaction`)に `project_id` / `dept_id` / `office_member_id` / 金額 / 計上日 が揃っており、`project_id`・`office_member_id` でサーバー側フィルタも可能。プロジェクト・従業員・部門の各マスタもAPI取得できる。
- **タスク0の設計を修正した4点**:
  1. **製品ごとにOAuth・APIのエンドポイントとスコープが異なる**ことが判明(経費は `expense.moneyforward.com/oauth/authorize`、スコープは `office_setting:write` 等の独自体系。請求書は `mfc/invoice/data.read`)。→ 製品別設定 `money-forward-product.config.ts` として抽象化し、業務モジュールから差異を隠蔽する構成に変更。
  2. **レート制限の具体的な数値は公式非公開**で「エンドポイントごとに独立、状況により変化」とのみ記載。経費APIのSwaggerには429の記述すらない。→ 固定スロットルのハードコード前提を撤回し、**429ベースの適応的バックオフを主軸**、判明済みの値(請求書の1秒3回)のみ設定として併用する方針に変更。
  3. **ページング方式も製品ごとに異なる**(経費は `page` + `next`/`prev` パス方式で `per_page` が使えず、共通仕様の `cursor`/`limit` と不一致)。→ 共通クライアントがページングを吸収し、業務モジュールには統一インターフェースを提供する責務を追加。
  4. **経費はread専用スコープが存在せず** `office_setting:write` が必須。→ 最小権限が取れないことを受け入れ、トークン保護(暗号化保存・Secrets Manager)を徹底する方針を明記。
- **その他の重要な判明事項**:
  - **データ連携用のWebhookは存在しない**。同期はポーリング型バッチ前提。
  - **経費明細に `updated_at` での絞り込みがない**(レスポンスには含まれるがクエリ不可)。→ 計上日ベースで直近数ヶ月をローリング再取得し `updated_at` 突き合わせで upsert する設計になる。
  - トークンは承認したユーザーの権限で発行されるため、**事業者全体のデータ参照には管理者権限ユーザーでの認可が必要**。バッチ用に管理者アカウントを1つ用意する運用になる。
  - トークン有効期限は製品ごとに大きく異なる(経費は約32日)。固定値を仮定せず `expires_in` から算出する。
  - **運用上の前提**: APIは入力された値を返すだけなので、MF経費側でプロジェクト機能を有効化し**経費登録時のプロジェクト選択を必須にする運用**がないと、原価がプロジェクトに寄らない。実装前に運用ルールの整備が必要。
- **検討候補として記録**: **マネーフォワード クラウド個別原価**が2025年11月にAPI提供を開始している(プロジェクト別工数管理・個別原価計算、労務費計算と間接費配賦)。要件が労務費・工数まで含む場合はこちらが適合し、給与連携(タスク5)の代替にもなり得る。ただし仕様は非公開でMF担当者への問い合わせが必要。MF経費のプロジェクトマスタは個別原価と同期する旨が公式記載されているため、「経費(実費)+ 個別原価(労務費・工数)」の組み合わせが本来のプロジェクト別原価の姿になり得る。
- **次のアクション**: タスク0の実装計画(plan)作成。あわせて、クラウド個別原価APIをMF社に問い合わせるかを判断する。

## 2026-07-27 タスク0の実装計画作成

- **経緯**: spec のマージを受けて、タスク0の実装計画を作成した。詳細は [design/2026-07-27-task0-mf-api-foundation-plan.md](design/2026-07-27-task0-mf-api-foundation-plan.md)。
- **計画の範囲**: **alphadb(スキーマ)+ alphaexapi(money-forwardモジュール)まで**とし、AWS Secrets Manager 導入とECSへのシークレット注入は対象外とした。理由: alphaexapi のECSタスク定義へのシークレット注入経路が未確定で、含めると着手前に調査待ちになる。この範囲ならMF実APIもAWS変更も不要で、モックによる単体テストで完結する。
- **実装は別リポジトリのため、alphadb と alphaexapi でそれぞれ別ブランチ・別PRになる**(12タスク構成)。
- **既存コードベース調査で判明した制約と、それに対する設計判断**:
  - **alphaexapi は現在ローカルでビルドできない**。`alphadb` が AWS CodeArtifact 配布の private パッケージで未インストールのため、`npm run build` が9件のエラーで失敗する。
    - → 対策として `MfPrismaPort` という最小インターフェースを alphaexapi 側で宣言し、モジュール配線時に `useExisting: PrismaService` で実装を注入する設計にした。これによりリポジトリの単体テストがレジストリ認証なしで完結する。依存の向きを逆転させる設計上の利点もある。
  - **テストが実質存在しない**(`app.controller.spec.ts` の1ファイルのみ)。テストパターンの確立も計画に含めた。
  - **複合ユニーク制約(`@@unique`)の使用例が既存スキーマにない**。`MfLink` で初めて導入する。「1エンティティ・1製品につきMF側IDは1つ」をDBで保証するために必要と判断。
  - **スケジューラが未実装**(alphabatch はSQS投入→worker実行方式)。定期同期が必要になるタスクで別途用意する。
- **設計上の重要な判断**:
  - **OAuth `state` はHMAC署名で完結させ、DBに保存しない**。ECSが複数タスクで動いてもどのタスクがコールバックを受けても検証でき、テーブルを増やさずに済む。有効期限はMF側の認可コード有効期限に合わせ10分。
  - **リフレッシュの直列化はPostgreSQLのアドバイザリロック(`pg_advisory_xact_lock`)を使う**。行ロックではなく名前付きロックにすることで、行が存在しない場合も直列化できる。
  - **`/callback` には既存の `GoogleAuthGuard` を適用できない**。MFからのブラウザリダイレクトで呼ばれるため Google IDトークンや `x-user-role` ヘッダーを持たない。`/authorize` にのみガードを付け、`/callback` は `state` の署名検証で保護する。
  - **レート制限の事前スロットルはプロセス内の情報しか持たない**ため、ECS複数タスクでは全体のレートを厳密に保証しない。429を減らす緩和策と位置づけ、適応バックオフを主軸とする。
- **完了後に別途必要な残作業**: alphadb の CodeArtifact への publish(外部影響のある操作なので実施前に確認)、MFクラウドの製品ごとのアプリ登録(全権管理者権限が必要。この時点で会計・請求書・債務支払の実際のURL・スコープが判明する)、Secrets Manager 導入とECS注入、実環境での疎通確認、alphasys側の管理画面導線。

## 2026-07-27 alphaaimail統合の基本方針確定(契約締結を境界としたデータ所有権)

- **経緯**: 上記検討資料の「3.1 対応表」について方針の指示があり、3章を改訂した。
- **確定した基本方針**:
  1. 契約締結以前(案件レベル)は alphaaimail 側のテーブルを使用する
  2. 契約締結時に、alphaaimail 側のテーブルから社内システムへコピーする
  3. 契約締結以降は社内システムに寄せる
- **この方針の効果(重要)**: 同じ案件を2システムで並行管理する期間が発生しないため、統合の課題が「**2つのDBを継続的に突き合わせる**」問題から「**締結時に一度だけ写す**」問題に変わった。結果として、当初「統合の前提課題」としていた以下は重要度が下がった。
  - **名寄せ品質**(companies 59件の表記ゆれ): 全件の自動突合が不要になり、締結する案件のみ人手確認すればよい
  - **金額の充足率17%**: 正式金額は締結時に社内システムで入力するため、金額による自動照合を行わない
  - **doc_number の重複**: 締結時に人が対象を選ぶため自動処理を壊さない。事前の一括重複解消が不要
  - → 逆に重要度が高いまま残るのは「**From/To/Cc アドレスの保存改修**」と「**先方担当者テーブルの新設**」の2点。締結時の担当者登録と締結後メールの紐付けに必須。
- **フェーズ1の位置づけが変わった**: 「全件を自動突合するバッチ」ではなく「**締結時に一度写すコピー機能**」になる。人手確認が締結という業務判断に自然に組み込まれるため、自動突合の前提条件(名寄せ精度・金額精度・番号重複解消)を満たす必要がなくなり、難度と範囲が下がった。
- **設計上の追加事項**:
  - `alp_mail_link` に `copyStatus` / `copiedAt` を追加。同一 deal の二重契約化を防ぐ冪等性の担保と、締結前後の判別に使う。

## 2026-07-28 project の定義確定 — メール由来データとは無関係

## 2026-07-28 補足: Project の紐付けは deal 時点でも可能(締結時に限らない)

- **経緯**: 上記で「Project の割り当ては締結時に管理担当者が判断」と書いたが、**deal の時点でも特定できる場合がある**との補足を受けて修正した。あわせてダッシュボードに Project を出す方針が確定した。

  | deal の性質 | Project の特定 | 扱い |
  | ---- | ---- | ---- |
  | **既存契約に関連する案件**(要員増員、契約延長など) | deal の時点で特定できる | **既存 Project への紐付けを手動で行う**。締結を待たない |

- **ダッシュボードに Project を出す方針が確定**。営業中・契約中の双方でグルーピング軸として使う。
  - **契約中**: 客先要請で1業務が複数契約に分割された場合、Project 単位でまとめると業務としての実態が見える
  - **営業中**: 既存契約関連の案件は deal 時点で Project が特定できるため、**既存 Project の下に進行中の引合を並べられる**(「この案件で増員の話が2件動いている」が一目で分かる)

### 一括管理方針(検討結果)

| 対象 | 保管先 | ローカル開発 |
| ---- | ---- | ---- |
| APIキー類(BANKCODE、Anthropic 等)、OAuth Client Secret | **SSM パラメータストア(SecureString)** | `.env`(生成物) |
| DB接続情報 | **Secrets Manager**(RDS自動生成) | `.env` の `DATABASE_URL` |

- パラメータストアを選ぶ理由: **無料**(Standard)なので項目を細かく分けられ、パス単位(`/alpha/<環境>/<プロジェクト>/<キー>`)でIAM権限を切れる。Secrets Manager は項目ごとに課金されるためコスト回避でJSONに詰め込むことになり、項目単位の権限分離ができなくなる
- **本番では `.env` を使わない**。ECS タスク定義には値ではなくパラメータのARNを書き(`ecs.Secret.fromSsmParameter` / `fromSecretsManager`)、ECSが起動時にIAM権限で取得して環境変数として注入する。**平文がタスク定義に載らなくなる**
- **アプリのコードは変更不要**。ローカルも本番も `process.env.X` を読むだけで、違いは「誰が環境変数を用意するか」のみ
- ローカル用の `.env` 生成コマンドは**開発用パス(`/alpha/dev/...`)を既定**とし、本番の値をローカルに降ろせないようにする(降ろす仕組みを作ると同じ事故が形を変えて再発する)
- **再発防止をセットにする**: `gitleaks` を pre-commit フックに入れる。GitHub のシークレットスキャンは private リポジトリでは GHAS 契約が必要なため、ローカルフックが実用的

### DB接続情報の扱い(方針確定)

**環境変数に `DATABASE_URL` があればそのまま使い、無ければ部品から組み立てる。**

```
if (process.env.DATABASE_URL) return process.env.DATABASE_URL;   // ローカル
return compose(DB_USER, DB_PASSWORD, DB_HOST, DB_PORT, DB_NAME); // 本番/ステージング
```

- 部品は**アプリがSDKで取得せず、ECSに注入させる**(`ecs.Secret.fromSecretsManager(secret, 'password')` 等)。アプリにAWS SDKを持ち込まず、VPCエンドポイントも起動時API呼び出しも不要になる
- **この形を最初に入れておくことが要点**。後から自動ローテーションを有効にする際、`addRotationSchedule()` の追加とVPCエンドポイントの用意だけで済み、**アプリのコードもURL形式も触らない**。逆に `DATABASE_URL` 1本で持つ形にすると、後でローテーションを入れる際にアプリ変更が必要になる

### 「Prisma は Secrets Manager に合わないのか」への回答

**合わないわけではない。** 当初4つの落とし穴を並べたため誤解を招いたが、原因を切り分けると次のとおり。

| 落とし穴 | 本当の原因 | Prisma固有? |
| ---- | ---- | ---- |
| 1. ローテーション時に稼働中タスクが古い値を持つ(再起動が必要) | コネクションプール + ECSの注入タイミング | いいえ |
| 2. `prisma migrate` は `DATABASE_URL` しか読めない | Prisma CLI の仕様 | **はい**(エントリポイント1行で解決) |
| 3. 自動生成パスワードの記号でURLが壊れる | DSN文字列形式全般 | いいえ |
| 4. 既存DBのマスターパスワードが変わる | 既存CFn構成からの移行 | いいえ |

- **Prisma固有は2番だけ**。1番と3番は単一DSN文字列を受け取る仕組み全般の問題(Rails の `DATABASE_URL` 等でも同じ)
- **本当の論点は「自動ローテーションを今入れるか」**。1番とローテーションLambdaのVPCエンドポイント/NAT要件は、ローテーションを入れなければ発生しない
- **RDSは未稼働**と確認できたため、**4番は完全に消滅**。最初から `Credentials.fromGeneratedSecret()` で作れる
- 3番の対策は両面から: 生成側で `excludeCharacters: '/@":\\\'?#%&+ '`、アプリ側で `encodeURIComponent`。生成側だけに頼ると手動設定値で事故る

## 2026-07-28 シークレット管理 設計書の作成とローテーション構成の確定

詳細は [design/2026-07-28-secret-management-design.md](design/2026-07-28-secret-management-design.md)。

### 確定したローテーション構成

| 対象 | ローテーション | 戦略 | 用途 |
| ---- | ---- | ---- | ---- |
| マスターユーザー | **自動** | `single user` | ローテーションLambda、`prisma migrate`、DBA作業 |
| アプリユーザー | **自動** | `alternating users` | アプリ(alphasys / alphaexapi)の接続 |

- **前回の助言を訂正した**。前回「マスターは手動ローテーション」としたが、**手動の方がリスクが高い**。DBのパスワードだけ変更して Secrets Manager 側の更新を忘れると、マスターシークレットを使うアプリユーザーの自動ローテーションが**静かに失敗し続ける**。自動化すればこの同期漏れは構造的に発生しない。
- **マスターの自動ローテーションはアプリに影響しない**。アプリが持つのはアプリユーザーの資格情報のみで、マスターを使うのはローテーションLambda・マイグレーション・DBA作業に限られ、いずれも短命または都度取得のため。
- **マスターに `alternating users` が使えない理由**: この戦略は「別の特権資格情報(`masterarn`)を使って対象のパスワードを変更する」仕組みで、対象がマスター自身だと渡すべき特権シークレットが存在しない。またユーザーを複製するため、スーパーユーザーが2つできてしまう。`single user` ならマスター自身でログインして自分のパスワードを変更するだけなので成立する。

### 再起動のタイミング(アプリユーザー)

- **AWSに組み込みのトリガーは存在しない**。ECSがシークレットを解決するのはタスク起動時のみで、ローテーション後も稼働中タスクは古い値を持ち続ける。
- `alternating users` では**前世代の資格情報が1ローテーション周期分有効に残る**ため猶予がある。周期90日なら「1周期に1回以上タスクが入れ替わっていればよい」。
- **方針: 通常のデプロイに便乗する(自動化しない)**。周期90日に対しデプロイが月1回程度あればマージンは十分で、EventBridge や Lambda を増やさない分「静かに壊れる」箇所も増えない。
- 必要になった場合の選択肢: ①ローテーション連動(EventBridge → Lambda → `forceNewDeployment`。2026年7月から Secrets Manager が EventBridge へ直接イベント発行するようになった) ②定期実行(週次の強制デプロイ。ローテーションに依存せず**パラメータストア側の変更も反映できる**ため使い道が広い)
- **注意点**: PostgreSQL はパスワード変更時に既存接続を切らないため、猶予を過ぎても**新規接続が必要になった瞬間だけ失敗する**。断続的な認証エラーとして現れ原因が分かりにくい。CloudWatch アラームが必要。

### 調査で解決したタスク0の未確定事項

**ECSタスク定義へのシークレット注入経路が判明した。** `alphasyscdk/lib/constructs/ecs.ts` の1箇所に集約されており、**同一タスク定義に alphasys(Frontend、3000番)と alphaexapi(Backend、3001番)が同居**している。`alphaexapi/infrastructure.yml` は CI/CD 用(ECR・CodeBuild・IAM)でタスク定義ではなかった。タスク0 spec / plan の該当箇所を解決済みに更新した。

### 確認が必要な事項(設計書12章)

- **マスターパスワードのコピーが Secrets Manager の外に存在しないか**(CodeBuild/CIの環境変数、`prisma migrate` の実行方法、開発メンバーのローカル `.env`)。存在するとそこだけ古い値で取り残されて壊れる
- アプリユーザーに与える権限の設計(現状アプリはマスター権限で接続。マイグレーション=マスター、アプリ=DML のみとする想定)
- ローテーションLambdaのネットワーク要件(Secrets Manager の VPC エンドポイント、または NAT 経由の外向き通信が必要)
- alphabatch の実行基盤(`ecs.ts` のタスク定義に含まれないため注入経路が別にあるか)

### 検討した代替案(7.6 に追記): マスターを2つ用意して相互にローテーションする案 — 採用せず

「マスターを2つ(`master_a`/`master_b`)作り、`master_a` のローテーションは `master_b` の資格情報で行う」という構成を外部記事で提示され、見解を求められた。**single user では Lambda が「今から変更するパスワード」でログインするため、処理中断でロックアウトされ詰む**という懸念に基づくもの。

懸念自体は実在するが、以下により採用しないと判断した。

1. **RDS のマスターパスワードは常に復旧できる** — `modify-db-cluster --master-user-password` で強制リセット可能。最悪でも「手動リセット + シークレット同期」で済み、**恒久的に詰まない**。RDS 自体が上位の管理者として振る舞えるため、一般ユーザーのロックアウトとは性質が異なる
2. **AWS の機構に回復手段が組み込まれている** — 旧バージョンが `AWSPREVIOUS` として1周期保持され "last known good" になる。またローテーション関数は `AWSCURRENT` でのログイン失敗時に `AWSPENDING` を試す(前回試行でDB側だけ変更済みのケースの回復)
3. **この構成は AWS の MultiUser(alternating users)ではない** — AWSのそれは対象ユーザーを**複製**し**固定の管理者シークレット**で変更する非対称な仕組みで、`master_b` は使われない。記事の対称構成を実現するには**カスタムLambdaの自作が必要**で、上記2の回復機構も自前実装になる
4. **リスクの総量が減らない** — スーパーユーザーが2つになりセキュリティ上は後退。かつ相互依存が生まれ、「自己変更のリスク」を「相互依存のリスク」に置き換えただけ
5. **AWS の推奨と整合しない** — AWSは single user を「最も単純でほとんどのユースケースに適切」とし、特に「**一時的(アドホック)または対話的なユーザー**に推奨」。本設計のマスターの使い方はこれに該当する。またAWSがロックアウト防止として推奨するのは「別の管理者シークレットでアプリユーザーのローテーションを担わせる」構成であり、**本設計の alternating users がまさにそれ**

なお公平を期すため、この代替案が正当化される条件(マスターを長期稼働アプリが常用/RDS以外で上位リセット手段が無い/ローテーション頻度が高い)も設計書に併記した。**本設計は「アプリにマスターを使わせない」ことでこれらの前提を消している。**

## 2026-07-30 staging取り残しの解消と、staging→mainのPR自動化という課題の発見

alphasyscdk / alphasys / alphaexapi の3リポジトリとも、`main` を `staging` にマージして乖離を解消した(各リポジトリの `feature/merge-main-into-staging` PR、マージ済み)。あわせて alphadb 側でも移植漏れのスキーマ変更(alp_skill_additionals へのカラム追加)を別PRで対応。

マージ作業では、**git の自動マージがコンフリクトとして検出せず一方の変更(主に main 側)を無言で破棄するケースが多数見つかった**(alphasyscdkではECRやGitHub接続の RemovalPolicy が意図せず DESTROY に戻る等、実害のある事例も)。そのため、コンフリクトマーカーだけを信頼せず、両ブランチの全差分ファイルを手動で突き合わせて確認する方針で対応した。alphasys/alphaexapi では大半が「staging が main より後から同じ機能を発展させたもの」で実害は無かったが、alphadb 一元化(A-2)へのフィールド名/enum リネーム追従漏れ等は実際に修正が必要だった。

**新たな課題として次を記録**：`staging` へのマージを契機に `staging` → `main` のPRを自動作成する仕組みが欲しい。今回のような「`staging` が `main` から数ヶ月分取り残される」事態の再発防止になる。詳細は [design/2026-07-30-branch-strategy.md](design/2026-07-30-branch-strategy.md) の「6. 課題」に記載。

## 2026-07-30 alphadb の `main` ブランチの位置付けに関する留保

alphadb-publish CodeBuild が対象ブランチを明示指定していない（デフォルトブランチ＝`main`）と判明したのを受けて、alphadb の `main`/`staging` の役割を再確認した。

- alphasys/alphaexapi の `main` は「push → 本番サービスのローリングアップデート」という実際の役割を持つ。
- 一方、alphadb の唯一のリリース動作は npm publish で、これは「Artifact は共有アカウント（ステージング）側で作る」という他の運用方針に厳密に合わせるなら `staging` を対象にすべきもの。しかしそうすると、alphadb の `main` は**他プロジェクトとのブランチ命名を揃える以外の意味を持たなくなる**。
- **結論**：矛盾は認識した上で、今回は変更せず保留とする。alphadb-publish の対象ブランチもこのまま（デフォルトブランチ＝`main`）にしておく。設計書（[design/2026-07-30-branch-strategy.md](design/2026-07-30-branch-strategy.md) 2章）に留保として記載した。

## 2026-07-30 alphadb staging ブランチの誤削除・復元と、main/staging 削除保護の検討

alphadb-publish CodeBuild の調査中に、`origin/staging` が PR#8（CodeArtifact認証トークン修正）を含まない古い状態に戻っていることに気づいた。`origin/main` には PR#8 の内容が含まれていたため、`staging` だけが取り残されているように見えた。

確認したところ、**main へのマージ後に alphadb の `staging` ブランチを削除し、その後 GitHub の restore 機能で復元していた**ことが判明。復元自体は成功しており、`main`/`staging` は再fetch後に完全同期していることを確認した(実害なし)。

## 2026-08-06 シークレット管理 Task 6 の実施と、alphadb のバージョン運用の確定

### 発端: デプロイしても DB に接続できない状態だった

移行計画の Task 1〜5 が完了する一方 **Task 6(アプリ側の切替)が未着手**で、次の不整合が残っていた。

- ECS のタスク定義は `DB_USER`/`DB_PASSWORD`/`DB_HOST`/`DB_PORT`/`DB_NAME` の5部品を注入する形に変わっていた
- 一方アプリは `new PrismaClient()` を引数なしで呼んでおり **`DATABASE_URL` しか読まない**
- その `DATABASE_URL` はもう注入されないため、デプロイしても接続に失敗する状態だった

### 対応範囲は「アプリのみ」だった

「アプリ / CI・CD / ローカル」の3面を確認したところ、**手を入れる必要があったのはアプリ側だけ**だった。

| 面 | 供給方法 | 対応 |
| --- | --- | --- |
| アプリ実行時 | `DB_*` 5部品を appUserSecret から注入 | 要変更（`buildDatabaseUrl()` を呼ぶ） |
| alphasys の Docker ビルド | 無し | 要変更（ビルド用ダミー1行） |
| `prisma generate`（alphadb publish） | buildspec の `env.variables` にダミー | 対応済み |
| `prisma migrate deploy` | masterSecret の5部品を注入し buildspec で組み立て | 対応済み（Task 5） |
| ローカル | `.env` の `DATABASE_URL` | 変更不要 |

**`prisma generate` にダミーが要る理由**は Prisma 一般の仕様ではなく、alphadb が `prisma.config.ts` を使っており `env("DATABASE_URL")` が**設定ファイルの読み込み時点で評価される**ためである。設定ファイルは CLI の全サブコマンドで読まれるので、DBに接続しない `generate` でも値が必須になる。publish ビルドはDBに触れないため、**このダミーは実資格情報に置き換えない**（置き換えれば平文の在り処が1箇所増えるだけ）。

### alphadb のバージョン運用: 開発初期は `1.0.0` を上書きし続ける

**方針(確定)**: 実運用のメンテナンスでは当然に版数を上げるが、**開発初期の間は `1.0.0` のまま上書き publish を繰り返す**。

障害となっていたのは、buildspec に「同一バージョンが既に存在すれば publish をスキップ」する処理が**初期コミット(2026-06-16)から入っていた**こと。`staging` に push しても CodeBuild は publish せずに終わっており、この運用と矛盾していた。CodeArtifact は既存バージョンへの上書きを拒否するため、`delete-package-versions` で削除してから publish する形に変更した(alphadb #12)。

- **⚠️ 削除処理と `codeartifact:DeletePackageVersions` 権限(alphasyscdk #48)は、いずれも「開発初期のみ」の措置。** 本番リリース後にこれらが残っていると、CI がリリース済みバージョンを消せてしまう。版数を上げる通常運用に切り替える時点で、buildspec の削除ブロックと IAM 権限の両方を外すこと。コード内にもコメントで明記した
- 削除は publish 直前(post_build)に置いた。pre_build で消すと、後続フェーズが失敗したときに「消しただけで publish されていない」空白状態が残るため

### 訂正: 同一バージョンを上書きしても integrity は変わらない

当初「上書きすると `npm ci` が EINTEGRITY で落ちるので `package-lock.json` の更新が必要」と判断していたが、**実測の結果これは誤りだった**。

npm はパッケージ tarball 内の mtime を正規化するため、**同じ内容を再 publish すればバイト単位で同一の tarball が生成され、ハッシュも変わらない**。実際に `alphadb@1.0.0` を削除して publish し直した後も、alphasys / alphaexapi の lockfile の alphadb エントリに変更は発生しなかった。EINTEGRITY が問題になるのは**中身を変えて同一バージョンで上書きしたとき**だけである。

## 2026-08-28 Track1 シークレットの staging 登録完了と、npm レジストリ設定の整理

### SSM 登録が `--apply` で全件失敗した — ドライランでは絶対に露見しない不具合

`register-secret-parameters.py` を staging に対して `--apply` したところ、**全件が `You must specify a region` で失敗**した。`aws ssm put-parameter` はリージョン必須だが、スクリプトが `--region` を渡していなかった。

**なぜドライランで気づけなかったか**: `put_parameter()` は `dry_run` のとき AWS を呼ばずに即座に `True` を返す作りになっている。つまり**ドライランは「値が読めるか」しか検証しておらず、AWS 呼び出し側の不備は `--apply` して初めて出る**。ドライランが通ったことを「登録できる」の根拠にしてはいけない。

**「`AWS_PROFILE` を環境変数で指定しているのに、なぜリージョンが必要なのか」**: `AWS_PROFILE` が解決するのは**認証情報**であって、リージョンは `~/.aws/config` の当該プロファイルに `region = ...` が書かれている場合にのみ一緒に解決される。書かれていなければリージョンだけ未解決のまま残る。今回がまさにその状態だった。

- `~/.aws/config` 側はユーザーが対応。
- スクリプト側も、**aws CLI の設定に依存せず単体で完結する**よう修正した(`AWS_REGION` / `AWS_DEFAULT_REGION` があればそれを使い、無ければ `ap-northeast-1`)。`put-parameter` と `sts get-caller-identity` の両方に渡す。
- alphasystem PR #31 → #32 で main まで反映済み。

修正後、**staging の SSM 登録は成功**。

8/13 に alphadb で3つのコミットが**同日に**入っていた。

| 順序 | 内容 |
| --- | --- |
| 1 | **1.1.0 リリース** — Track1 スキーマだが `updatedAt` なし |
| 2 | `updatedAt` を Track1 テーブルに追加 |
| 3 | **1.2.0 リリース** — 上記の修正込み |

alphaexapi の lockfile は **1.1.0 のまま**で、1.2.0 に上げられていなかった。
一方 DB マイグレーションは `updatedAt` ありのスキーマから適用され、
`updated_at` は NOT NULL で作られている。

**`@updatedAt` はクライアント側で値を設定する機能**のため、クライアントが
カラムを知らなければ INSERT に含まれず、DB の制約で拒否される。
**スキーマを変えたら、利用側の版数を上げるまでが1セット。**

### 原因2: 失敗したメールを既読にしていた（設計上の欠陥）

保存の成否に関わらず UID を既読対象に入れていた。取り込み対象の選択は
`{seen: false}` なので、**一度既読にされたメールは二度と取り込まれない**。

原因1で298通すべてが失敗し、そのまま既読にされ、**DB 0件・IMAP 全件既読**
という取り残しが生まれていた。「失敗はログに出るから気付ける」つもりが、
実際には**取り込み対象がゼロになって静かに止まる**状態だった。

既読にするのは「再取得しても結果が変わらない」ものだけに限定した
（→ alphaexapi PR #63）。

| 結果 | 既読にするか | 理由 |
| --- | --- | --- |
| 保存成功・重複 | する | 再取得不要 |
| Message-ID / From なし | する | 再取得しても取り込めない。未読だと無限に再試行する |
| 例外で失敗 | **しない** | 復旧しうる原因が多い。次回に再試行させる |

**学び**: 外部システムの状態を「処理済み」に変える操作は、**成功した対象だけ**に
限定する。失敗を含めると再試行の道が閉じ、データ損失が静かに起きる。

既存テスト2件が旧挙動（失敗も既読にする）を**明示的に固定していた**ため、
期待値も更新した。テストが仕様として誤りを固定していた例。

### 原因3: 初回リリース前なのに版数が 1.2.0 まで上がっていた

一度もリリースしていないため 1.0.0 の上書き運用に戻した（→ alphadb PR #40/#41）。

8/6 に入れた上書き publish の仕組みは、**8/13 に意図的に撤回**されていた
（`ci: switch to plain npm publish, drop version-overwrite workaround`）。
それを知らずに「削除処理が消えている」と誤って判断した。
**履歴を確認せずに原因を決めつけない。**

CodeArtifact の 1.1.0 / 1.2.0 を削除して 1.0.0 のみ残したため、両アプリの
`^1.1.0` / `^1.2.0` が解決不能になり `ETARGET` が発生した。
上書き運用の間は**キャレットなしの固定指定**にした（`^1.0.0` だと将来
1.1.0 を publish した時点で意図せず追随する）。

> **初回リリース時に、buildspec の削除ブロックを必ず外すこと。**
> リリース済みバージョンを CI が消せる状態を残してはならない。

### 取り残し298通の回復

既読フラグを外して再取り込みさせた。`messageId` の一意制約があるため
重複登録は起きない。

**imapflow で UID の配列を渡すと `resolveRange` が `join(',')` で連結するだけ**で、
`packMessageRange` による圧縮は効かない。検索条件オブジェクト（`{seen: true}`）を
渡すと SEARCH 経由で `1:299` のように圧縮される。

`messageFlagsRemove` は**例外を投げずに `false` を返す**ことがあり、戻り値を
見ていなかったため「298件を未読化した」と表示しながら実際には何も変わって
いなかった。**成否を戻り値で返す API は必ず確認する。**

### CI/CD の自動化範囲（確認結果）

| alphasys / alphaexapi のイメージビルド | **する**（`staging` への push で webhook 起動） |

### 原因4: メールに NUL バイトが含まれていた

uid=175/272 の2通が必ず保存に失敗していた。ログを改善して初めて原因が見えた。

```
PostgresError { code: "22021",
  message: "invalid byte sequence for encoding \"UTF8\": 0x00" }
```

**PostgreSQL の text / varchar は 0x00 を格納できない。** パースは成功し
`create()` の実行時に拒否される。壊れた添付やエンコード宣言の誤りで発生し、
**送信側の都合なので受信側では避けられない。**

DBへ渡す文字列すべてから 0x00 を除去する方針とした（→ alphaexapi PR #68）。
どのフィールドに混入するかは送信側次第のため一律に適用する。改行やタブは
PostgreSQL に格納できるため触らない。

> **判断**: メール1通が丸ごと取り込めないことと、本文から制御文字が失われること
> を比べ、後者を選んだ。営業メールの可視化という目的からして軽微。

**学び**: 「パースは通るのに保存だけが必ず失敗する」類型は、DB の型が受け付け
ない値が混入している可能性を先に疑う。アプリのロジックを追っても出てこない。

### CloudWatch は「1行 = 1イベント」

**ログ設計上の制約として記録する。**

コンテナの標準出力は行単位でイベント化されるため、**改行を含むメッセージは複数
イベントに分割される**。`--filter-pattern` で検索できるのは1行目だけになり、
Prisma のような複数行エラーでは `code` / `meta` / スタックが別イベントに散る。

実際に `--filter-pattern "uid=175"` では次の1行しか取れず、原因が見えなかった。

```
メッセージの取り込みに失敗した（uid=175, 段階=保存, 7861バイト）: PrismaClientUnknownRequestError:
```

時刻範囲を指定して分割されたイベントを手作業でつなぎ、ようやく `22021` を確認できた。

**例外をログに出す際は1行に畳む。** 行ごとに trim して空行を落とし、区切り文字で
連結する（→ alphaexapi PR #68）。単純に改行を置換するだけでは、**空白だけの
メッセージが区切り文字になって「中身があるように見える」**（`Error: | at ...`）。

### 原因2の対処: 接続数1の PrismaClient でアドバイザリロック

`@Cron` は `@nestjs/schedule` が**プロセス内に持つスケジューラ**で、各プロセスが
自分の時計で発火する。`desiredCount: 2` なので同じ時刻に2回発火していた。
既存の `isRunning` はプロセス内変数のため別プロセスには効かない。

共有DBの `pg_try_advisory_lock` で排他した（→ alphaexapi PR #65）。
待たない `try` 版を使う。「他が動いているなら今回は諦める」が正しく、次の
ポーリングで再試行すれば足りる。待つ版だと全タスクが順番待ちして同じ処理を繰り返す。

**ロック専用に接続数1の PrismaClient を持つ。** ここが設計の要点。

`pg_try_advisory_lock` は**ロックを接続に結びつける**。通常の接続プール経由だと
取得と解放で別の接続が割り当てられうる。そうなると `pg_advisory_unlock` は
「保持していないロック」の解放となって失敗し、**ロックが接続の再利用まで残って
以降の取り込みが全てスキップされる**。しかも「たまたま動く」ことが多く質が悪い。

> **`connection_limit=1` を増やしてはならない。** 効率が悪いように見えるが、
> 増やすとこの問題が再発する。コードにも明記した。

トランザクション版（`pg_try_advisory_xact_lock`）は採らなかった。ロック保持には
取り込み全体をトランザクションで囲む必要があり、IMAP のダウンロードと AI 推測
（外部API）を含む数分の処理で `idle in transaction` が続くため。

EventBridge 方式（RunTask / controller）も検討したが、**「10分ごとに1回起動する」
ことは保証しても「前回の実行中か」は見ない**ため、処理が10分を超えると同じ問題が
別の形で再発する。インフラ変更と費用に見合わないと判断した。

## 2026-09-03 営業メール確認キューの設計と実装

取り込んだ299件が**全件「取引先未確定」で、確認キューから何も操作できない**
状態だった。ここから、人がメールを処理できる状態までを作った。

### `/sales/mail` が空だったのは仕様どおり

この画面は `MATCHED` / `REVIEWED_NO_CONTRACT` のメールを持つ顧客だけを表示する。
全件 `UNMATCHED` なら0件になる。**不具合ではない。**

行き詰まっていたのは確認キューの側で、契約の候補は `customerNo` から引くため、
**取引先が決まっていないメールは何も操作できなかった**。

### 確定した動線

```
UNMATCHED       取引先を選ぶ        → NEEDS_REVIEW
NEEDS_REVIEW    契約を選ぶ(複数可)  → MATCHED           → /sales/mail に表示
                どれにも該当しない  → REVIEWED_NO_CONTRACT
いずれの状態でも 無関係として削除    → DBとメールサーバーから完全削除
```

設計書の3段階に実装を合わせた。それまでは**ドメイン一致した時点で `MATCHED`**
にしており、`NEEDS_REVIEW` を一度も設定していなかった。人が指定した場合と
ドメイン一致の場合で状態が割れるため揃えた（→ alphaexapi PR #70）。

型を `'NEEDS_REVIEW' | 'UNMATCHED'` に狭めたことで、AI契約推測の起動条件
（`if (matchResult === 'MATCHED')`）をコンパイラが検出した。**狭めていなければ
推測が静かに動かなくなっていた。**

### SaaS ドメイン問題（設計の前提を突く指摘）

受発注や請求に **SaaS を使う取引先が複数あり、差出人が SaaS 事業者のドメインに
なる**。しかも同じ SaaS を複数の取引先が使う。

`alp_customer_domain.domain` は一意制約を持つため、SaaS ドメインを登録すると
**その SaaS を使う他の取引先のメールまで1社に誤って紐づく**。未確定のまま残るより
悪い状態になる。

一方、**件名や本文に会社名・契約名が入っているケースがあり、人が見れば判断できる**。

**確定した方針**: 操作を2つに分ける。

| 操作 | 対応表への影響 | 用途 |
| --- | --- | --- |
| 取引先を選ぶだけ | **なし** | **SaaS 経由**（既定の動線） |
| チェックを入れて確定 | ドメインを登録 | 取引先の自社ドメイン |

チェックボックスは**既定でオフ**。両画面に理由を明記した。

**学び**: 「ドメインで顧客を特定する」という前提自体が、SaaS の普及で崩れていた。
自動化の前提が業務実態と合っているかは、実データを見るまで分からない。

### ドメイン登録の口が存在しなかった

`alp_customer_domain` にデータを入れる手段が**alphasys にも alphaexapi にも
移行データにも無かった**。自動マッチングはこの表を引くだけなので、空である限り
全件 `UNMATCHED` になる。顧客管理画面と確認キューの両方に登録経路を作った。

誤登録を防ぐ検証を入れた。

- **自社ドメインの登録を禁止**（送信メールでは差出人が自社になるため、相手先
  ドメインは宛先側から導出する）
- **他社に登録済みなら取引先名を出して拒否**（一意制約で黙って失敗すると原因を
  追えない）
- `@` 付き・アドレス貼り付け・ドット無しを拒否し、小文字に正規化
  （マッチング側は小文字で引くため）

### 画面の絞り込み（実運用での指摘を反映）

- **取引停止（`sleep`）の取引先を選択肢から除く**
- **略称（`customerNick`）で表示**。正式名称は長く見分けにくい。未登録なら正式名称
- **プルダウン形式の絞り込みコンボ**。244件を並べても探せない。候補は入力欄に
  重ねて表示し、明細の高さを変えない
- **契約候補から終了済みを除く**。`contTo` 未設定は継続中とみなして含める

> 候補の選択は `onMouseDown` で行う。`onClick` だと入力欄の `blur` が先に走って
> 一覧が閉じ、クリックが届かない。

### 無関係メールの削除

取り込み専用メールボックスには**営業と関係のないメールも大量に届く**。確認キューに
残ると確認すべきメールが埋もれる。

**DBとメールサーバーの両方から完全削除する。** DBだけ消すと既読のままサーバーに
残り続けるため。**原本は各担当者のメールボックスにも配信されており、必要なら
再転送できる**（取り込み専用メールボックスは fan-out されたコピーの1つ）。この
前提があるため、取り違えても復旧可能と判断した。

`SalesEmail` は IMAP の UID を保持していないため **Message-ID で引く**。同じ
Message-ID は定義上同一のメールなので、複数一致してもまとめて削除してよい。

サーバー側の削除に失敗してもDBの削除は続行する。確認キューから消せない方が実害が
大きく、サーバーに残ったメールは既読のため再取り込みもされない。

### 削除したメールからの学習 → 同日に実装（差出人単位の除外ルール）

当初「ベース完成後の課題」としたが、**削除がユーザ処理の大半を占める**ことが
判明したため同日に着手した。

### PR の取り込み漏れ（段取りの失敗）

alphasys #146 の base を `feature/select-contracts-in-review` のままマージしたため、
**`staging` に入らなかった**。#145 は既にマージ済みで、#146 の変更（ドメイン登録の
11ファイル）はどこにも反映されず、機能が丸ごと欠落した状態でデプロイされた。

PR 本文に「マージ後に base を切り替えてください」と書いただけで、切り替え自体を
確実にしていなかったのが原因。

**再発防止**: PR は積まない。先行PRがマージされてから後続ブランチを切り直す。
やむを得ず積む場合は、先行PRのマージ直後に `gh pr edit <番号> --base staging` で

## 2026-09-03 無関係メールの自動除外（差出人単位の除外ルール）

確認キューが機能し始めた結果、**無関係メールの削除が確認作業の大半を占める**
ことが分かった。同じ差出人から繰り返し届くものにも毎回対応が必要だった。

### 検討した方式

| 方式 | 判定 |
| --- | --- |
| **差出人単位の除外ルール** | **採用。**確実で誤判定がほぼ無い。定期配信・通知に強い |
| 件名のパターン | 見送り。取引先の正当なメールが同じ語を含むと誤って消える |
| AI 分類 | 見送り。自動削除に使うと誤判定に気づけない。将来の候補提示用 |
| 一括削除（差出人でまとめる） | 段階1として提案したが、除外ルールを先に入れたため不要になった |

**AI を自動削除に使わない**のが方針上の要点。誤判定で取引先のメールが消えても
気づけないため、AI は「候補提示」までに留める。

### 確認は登録時の1回だけ

```
1回目: 削除するとき「今後この差出人も除外する」を選ぶ（ここで確認）
2回目以降: 取り込み時に自動で除外。確認キューにも出ない
```

**除外対象はメールサーバーからも削除する。** DBに保存しないだけでは既読のまま
溜まり続け、無関係なメールがメールボックスを占め続ける。

### 除外の単位を2つに分けた理由

| 単位 | 判定 | 意図 |
| --- | --- | --- |
| `ADDRESS`（既定） | 完全一致 | **同じドメインの別アドレスには広がらない。**取引先の担当者からのメールを残す |
| `DOMAIN` | `@` 以降が一致 | 効果は大きいが、同じドメインの商談も消える |

**アドレス単位が同じドメインに波及しないことをテストで固定した。** ここが単位を
分けた意図そのものであり、実装が崩れると静かにメールが失われる。

ドメイン単位は取引先の対応表（`alp_customer_domain`）と衝突する余地があるため、
既定にはせず明示的に選ぶ形にした。画面でも警告を出す。

### 誤登録に「後から気づける」設計

自動削除は都度の確認が無いため、**誤ったルールを登録すると以後黙って消え続け、
気づく機会がない。** これが方式の唯一の弱点であり、対処を設計に組み込んだ。

| 手段 | 内容 |
| --- | --- |
| `matched_count` | 除外件数。**想定より多く消していないか**が分かる |
| `last_matched_at` | ルールがまだ効いているか分かる |
| `note` | 登録の契機になったメールの件名。何を除外したのか辿れる |
| 管理画面 | 除外件数の**多い順**に並べ、ルールを削除できる |
| 取り込みログ | `除外12件` のように件数を出す |

**都度確認の代わりに、後から気づける仕組み**という位置づけ。操作の手間を増やさず
誤登録を検出できる。

### 実装上の判断

- **判定はパース後**に行う。差出人アドレスを取り出す必要があるため
- **ルールの登録は削除より先**に行う。削除だけ成功してルールが残らないと、次の
  ポーリングで同じ差出人のメールがまた入ってくる（順序をテストで固定）
- **登録は `upsert`**。`pattern` に一意制約があり、二重登録を弾くだけでは
  「登録できない」と見えて原因が分からない
- **表記は小文字に揃える**。メールアドレスの大文字小文字は区別されない運用が
  一般的で、揃えないと同じ差出人が一致しなくなる（`alp_customer_domain` と同じ方針）
- ルールを削除すれば**次のポーリングから効かなくなる**（取り込みはルールを毎回
  読み直す）。既に削除されたメールは戻らない

### 学習データの保持は不要だった

当初「削除前に判定材料を残す設計が必要」と考えたが、**除外ルールそのものが残る**
ため履歴の保持は要らなかった。

履歴が必要になるのは**AIに判断例を与える段階**だけ。その時点で「削除時に差出人と
件名を記録する」を追加すれば足り、本文まで残す必要はない。

### 原本が失われる点について

**メールサーバーからも完全削除するため、取り違えると原本が失われる。** ただし
取り込み専用メールボックスは fan-out されたコピーの1つで、原本は各担当者の
メールボックスにも配信されており再転送できる。この前提があるため、確認ダイアログ
以上の安全策は設けないと判断した。

## 2026-09-24 alphadb の Prisma エンジンが Linux 専用で、Windows のローカル起動が落ちていた件

### 症状

`alphaexapi` を Windows でローカル起動すると、TypeScript のコンパイルは通るのに実行時に落ちる。

```
PrismaClientInitializationError: Prisma Client could not locate the Query Engine for runtime "windows".
This happened because Prisma Client was generated for "debian-openssl-3.0.x", but the actual deployment required "windows".
```

### 原因 — `binaryTargets` の `"native"` は「generate を実行したマシン」に解決される

`alphadb/prisma/schema.prisma` の指定は `binaryTargets = ["native", "debian-openssl-3.0.x"]` だった。

**`"native"` は利用側のマシンではなく、`prisma generate` を実行したマシンのプラットフォームに解決される。** alphadb は `prepublishOnly: prisma generate` を持ち、publish は CodeBuild(Linux) 上で走るため、`"native"` も `debian-openssl-3.0.x` に解決される。結果として**配布物には Linux 用エンジンしか同梱されない**。

配布物の実体を確認したところ、エンジンは1つだけだった。

```
libquery_engine-debian-openssl-3.0.x.so.node   (17.5MB)
```

エラーメッセージの検索パスに `/codebuild/output/src3339599095/src/github.com/alphacmc/alphadb/generated/client` が出ているのが、CodeBuild の生成物がそのまま配られている決定的な証拠。ECS / Docker(Linux) では問題なく動くため、**Windows のローカル開発でしか露見しない**。

`schema.prisma` のコメントにある「生成物をパッケージ内に出力し、利用側は generate 不要」という設計自体が、暗黙に Linux 前提になっていた。

### 決定した方針

検討した3案のうち、**応急処置(C)で即座に作業を再開し、恒久対応(A)を並行して入れる**方針をユーザーが承認。

| 案 | 内容 | 採否 |
| --- | --- | --- |
| A | alphadb の `binaryTargets` に `"windows"` を追加して再 publish | **採用（恒久対応）** |
| B | alphaexapi 側の `postinstall` で `prisma generate` を走らせる | **不採用**。alphadb の「利用側 generate 不要」という設計に反し、Docker ビルドでも毎回走るため |
| C | `node_modules/alphadb` 配下で直接 `npx prisma@6.19.3 generate` | **採用（応急処置）**。ただし `npm ci` で消えるため繋ぎ |

**バージョンは 1.0.0 のまま据え置くと決定。** 理由はユーザーの明言どおり「**リリースもしていないものを上げるわけにはいかない**」。alphadb は PR #40（`78edb6b`）で 1.0.0 上書き publish 運用に戻しており、`origin/main` / `origin/staging` とも 1.0.0 であることを確認済み。

パッケージが Windows 用エンジン分（`query_engine-windows.dll.node` 約21MB）増える点は、許容する判断とした。

### 実施済み

- **応急処置(C)完了**。`node_modules/alphadb` で `npx prisma@6.19.3 generate` を実行し、`query_engine-windows.dll.node`(約21MB) が生成されたことを確認。Linux 用エンジンも `binaryTargets` に明示されているため残っている

- **恒久対応(A)は alphadb PR #44（Draft）**。`feature/add-windows-binary-target`。`prisma validate` 通過済み。同じ罠を繰り返さないよう、なぜ `"windows"` を明示するのかを schema.prisma のコメントに残した

### あわせて判明した運用上の注意 — record hook は受け皿の無いリポジトリでは無言で no-op になる

記録を促す `stop-record-decisions.sh` は、**カレントリポジトリ内**の `conversations.md` / `LEARNINGS.md` / 計画ファイルしか探さない（`[ -n "${CONV}${LEARN}${PLANS}" ] || exit 0`）。

今回のように `alphaexapi` で作業していると、受け皿が `alphasystem` 側にあるため**スクリプトは何も出さず終了コード0で終わる**。エラーも警告も出ないため、hook が機能していないことに気づけない。2026-09-07 に Windows で `jq` 未導入により無言 no-op になった件と同じ「静かに効かなくなる」パターン。

## 2026-09-24 Norton の TLS 傍受で AWS CLI が全滅していた件

`npm ci` が `E401 Unable to authenticate` で落ちたため CodeArtifact のトークンを取り直そうとしたところ、その手前で AWS CLI 自体が失敗することが判明した。

```
SSL validation failed for https://codeartifact.ap-northeast-1.amazonaws.com/...
[SSL: CERTIFICATE_VERIFY_FAILED] certificate verify failed: unable to get local issuer certificate
```

### 原因 — Norton が TLS を傍受しており、AWS CLI だけがその CA を知らない

`NODE_EXTRA_CA_CERTS` に `C:\ProgramData\Norton\Antivirus\wscert.pem`（Norton のルート CA、証明書1枚）が設定されている。Norton が全通信の TLS を傍受して自身の CA で署名し直しているため、その CA を信頼しないと検証に失敗する。

- **Node 系（npm・CDK の AWS SDK for JS）は `NODE_EXTRA_CA_CERTS` を読むので通る**
- **AWS CLI は Python 製（aws-cli/2.28.13 Python/3.13.4）で `NODE_EXTRA_CA_CERTS` を読まない**。そのため AWS CLI だけが全滅する
- `gh` は Go 製で Windows 証明書ストアを見るため通る

切り分けの決め手は **CodeArtifact だけでなく STS でも同じエラーが出たこと**。エンドポイント固有ではなく AWS CLI 全体の問題だと確定できた。

### 効いた対処

`AWS_CA_BUNDLE` に Norton の CA を指定すると通る。

```powershell
$env:AWS_CA_BUNDLE = "C:\ProgramData\Norton\Antivirus\wscert.pem"
aws sts get-caller-identity --profile staging   # → 570024666076 が返る
```

### 影響範囲（重要）

**`aws` コマンドを使うものはすべて巻き込まれる。** 特に:

- `scripts/register-secret-parameters.py` — 内部で `aws ssm put-parameter` / `aws sts get-caller-identity` を subprocess 実行しているため、`AWS_CA_BUNDLE` が無いと**全件失敗する**
- CodeArtifact のトークン取得 → これが無いと `npm ci` / `npm install` が E401 で落ちる

`cdk deploy` は AWS SDK for JS 経由なので `NODE_EXTRA_CA_CERTS` が効き、影響を受けない見込み。

### 注意点 — この対処は片肺になっている

`wscert.pem` には **Norton のルート CA 1枚しか入っていない**。`AWS_CA_BUNDLE` はバンドルを置き換えるため、この指定をすると **AWS CLI は Norton 署名の証明書しか信頼しなくなる**。Norton の傍受が全通信に掛かっている限り動くが、傍受が無効化・アンインストールされた場合や傍受を通らない経路が出た場合は再び壊れる。

恒久対応の方式（Norton の CA 単体を恒久設定にするか、公開ルート CA と結合したバンドルを作るか、AWS ドメインを Norton のスキャン対象から除外するか）は**未決定**。

### 補足 — `npm ci` は案C の応急処置を消す

予告どおり `npm ci` で `node_modules/alphadb` が入れ替わり、Windows 用エンジンが消えた。復旧後に `npx prisma@6.19.3 generate` を再実行して復旧済み。alphadb PR #44 の publish が済むまでは、`npm ci` のたびにこの再実行が必要。

### 対処方針の決定 — Web シールドを止める（案C）

HKLM:\SOFTWARE\Norton\Antivirus\properties\WebShield\Common

## 2026-09-24 alphadb の配布方式を「版数固定＋上書き publish」から 0.x 採番へ変更（決定）

### 経緯 — 今日の障害は現行方式の必然的な帰結だった

alphadb PR #44（Windows 用 Query Engine 追加）を publish したのに alphaexapi へ届かず、`package-lock.json` の integrity を手で更新してようやく反映された。ユーザーから「**alphadb の方式は運用に耐えない**」との問題提起があり、方式を見直した。

### 現行方式が耐えない理由（今日実証された分）

1. **消費側の lockfile integrity が追随しない** — publish しても届かず、全消費リポジトリの lockfile を手で更新する必要がある
2. **npm キャッシュも追随しない** — バージョンが同じなので再取得しない
3. **CI が公開済みパッケージを削除できる権限（`codeartifact:DeletePackageVersions`）を持ち続けている** — 事故れば全消し
4. **削除→publish の間に空白期間がある** — その瞬間に `npm ci` したビルドは失敗する
5. **どのビルドが入っているか追跡できない / ロールバックできない**

### なぜ ECR と同じ「上書き」が CodeArtifact ではできないのか

ユーザーの運用方針は「**正式リリースまでは MUTABLE で同じバージョンを上書きし、正式運用開始時に IMMUTABLE へ切り替える**」。ECR ではこれが成立している（実際に `alphasys-frontend` / `alphasys-backend` とも `MUTABLE`、untagged を7日で消すライフサイクルルールもある）。CodeArtifact でも同じ感覚でいた、というのが発端。

**これは原理的に不可能。** 理由は可変タグの有無ではなく、**解決のタイミング**にある。

| | 記録するもの | いつ解決するか | 付け替えが効くか |
| --- | --- | --- | --- |
| コンテナ | `imagedefinitions.json` に `repo:0.1.0` | **デプロイ時**に ECS が解決 | **効く** |
| npm | `package-lock.json` に version + **`integrity`(sha512)** | **lock した時点で解決済み** | **効かない** |

ECR は「タグ(可変)」と「ダイジェスト(不変)」が分離しているが、**npm にはその分離が無く、バージョンが識別子そのもの**。さらに決定的なのは、消費側の `package-lock.json` が**ダイジェストを固定してしまう**こと。レジストリ側で中身を差し替えても、手元の lockfile は古いダイジェストを要求し続けるため届かない。

> コンテナで同じ状況を作るなら、ECS がタグではなく **ダイジェスト(`repo@sha256:...`)でデプロイしている**状態を想像すればよい。その場合はタグを付け替えても何も起きない。npm は常にその状態。

現行の「削除してから publish」は MUTABLE の模倣だが、**レジストリ側だけ模倣できて消費側が追随しない**。今日の障害はその破綻。

### 決定した方式 — 案2（`0.x` 採番）+ 案4（消費側で generate）

段階運用の考え方はそのまま活かし、表現手段を「上書き」から「採番」に変える。

| | ECR（現行・継続） | CodeArtifact（新方式） |
| --- | --- | --- |
| リリース前 | `0.1.0` を MUTABLE で上書き | **`0.0.1` → `0.0.2` … と採番** |
| 正式リリース | `IMMUTABLE` に切替 | **`1.0.0` を publish**、以降は通常運用 |

`0.x` は SemVer で「公開 API は不安定」を意味するため、「**まだ正式リリースしていない**」という意思表示は、番号を止めることではなく `0.x` に留めることで表現する。**番号が増えること自体はリリースを意味しない。**

**検討して不採用にした案**:

- **案1 プレリリース版（`1.0.0-dev.N`）** — 案2 と機能は同等だが、`0.x` の方が alphasys / alphaexapi の現行版数（`0.1.0`）と揃う
- **案3 Git 依存（`github:alphacmc/alphadb#sha`）** — 版数不要だが、Docker ビルド内で GitHub 認証が必要になり、**IAM 由来の短命トークンが長命の GitHub トークンに後退する**
- **案5 Git submodule + `file:` 依存** — 版数不要かつ認証も増えないが、**社内で alphadb だけ別方式**になる。「alphadb だけ勝手が違う」状況を再び作ることになるため不採用

**案4（消費側で `prisma generate`）は併せて採用**。ユーザーの「開発時に generate するのは何の負担にもならない」との判断による。これにより:

- 今日の `binaryTargets` 問題が**構造的に消える**（各環境の `native` で生成されるため）
- 配布物が **21MB → 数十KB** になる

### 運用手順（確定）

**alphadb 側**: バージョンは**ユーザーが手動で変更**する（`0.0.1` から開始）。自動採番はしない。

**消費側（alphasys / alphaexapi）**: **`package-lock.json` を手で編集してはいけない。** lockfile は version / resolved / **integrity(sha512)** の3点を持ち、integrity は tarball の実ハッシュなので手では作れない。バージョン文字列だけ書き換えると `npm ci` が整合性検証で失敗する。

正しい手順は各リポジトリで次を実行し、`package.json` と `package-lock.json` の**両方をコミット**する。

```bash
npm install alphadb@0.0.2
```

⚠️ **alphasys と alphaexapi は同じ共有DBのスキーマを見るため、必ずセットで更新する。**

### 撤去するもの

- alphadb `buildspec.yml` の**既存バージョン削除ブロック**
- alphasyscdk の IAM から **`codeartifact:DeletePackageVersions`**
- alphadb の `generated/` 同梱（案4 により不要）

### 付随して判明した要対応事項

**ECR の `imageTagMutability` がコードと実態で乖離している。**

| | 値 |
| --- | --- |
| AWS の実態 | **MUTABLE**（意図どおり） |
| `alphasyscdk/lib/constructs/ecr.ts` の既定値 | **IMMUTABLE** |
| `cdk.json` / `cdk.context.json` の context 指定 | なし |

段階運用の意図がコードに書かれていないため、**次に SharedStack をデプロイした時点で意図せず `IMMUTABLE` に切り替わり、イメージ push が `ImageTagAlreadyExistsException` で止まる**。`cdk.json` の context に `"imageTagMutability": "MUTABLE"` を明示し、正式運用開始時にそれを外す（または `IMMUTABLE` にする）のを切替手順とする。**未実施。**

本セッションで、`main` を base にして PR を作るという逸脱をした（alphadb #44 / alphaexapi #76 / alphasystem #50）。`docs/design/2026-07-30-branch-strategy.md` に「**`main` から直接ブランチを切ってはいけない**」と明記されており、**同書セクション4には Claude が過去に同じ逸脱をした記録**まで残っていた。

## 2026-10-08 設計バグ判明 — プロジェクト受発注一体化により、契約（Contract）が取引先を持たない

alphasys課題表（請求一覧・21行目「仕入側の取引先名表示を発注先にしたい」）の調査中にユーザーが発見。
**alphasys課題の個別修正は、この件の方針が決まるまで中断する。**

### 経緯

21行目「仕入を選択した場合、表示される取引先名が受注先のままになっている。契約の取引先（発注先）としたい」
を調査する過程で、`alphadb` のスキーマを確認したところ `Contract`（契約）テーブルに
取引先番号（customerNo）を持つカラムが存在せず、`Project`（プロジェクト）経由でしか
取引先を解決できない構造であることが判明。これをユーザーに共有したところ、設計上のバグだと
指摘があった。

### 現状の設計（受発注一体化後）

- プロジェクトは受発注が一体化されており、**受注駆動**のため常に「受注取引先」を保持している
- 契約（Contract）はプロジェクトに属しているが、契約自体は取引先番号を持たない
- そのため、仕入（発注）契約の「発注先（仕入先）」の取引先を解決する手段がデータモデル上
  存在しない。現行の請求一覧画面は、仕入請求でもプロジェクトの受注取引先を表示してしまっている
  （バグ）

### 以前の設計（参考）

プロジェクトは発注・受注で分かれており、発注プロジェクトは対応する受注番号を保持していた
（`alp_contract.order_contract` は、発注契約の場合に対応する受注契約番号を持ち、受注契約では
NULL、発注の仮契約（対応する受注契約が未決）では`0`になる — という業務仕様は確認済み）。

### 想定される対応（まだ決定ではない）

契約テーブル（`alp_contract`）に取引先番号カラムを追加せざるを得ないのではないか、という
ユーザーの所感。ただし、影響範囲（既存データの移行、Project側の取引先との整合性、
プロジェクト一覧・契約一覧・請求一覧など参照箇所すべて）の洗い出しと設計判断が必要。

### 仕様確定（2026-10-08）

論点①②も決着し、仕様が確定した。内容は別文書にまとめた。

→ [docs/design/2026-10-08-契約への取引先追加-仕様.md](design/2026-10-08-契約への取引先追加-仕様.md)

| 論点 | 決定 |
| --- | --- |
| ① 受注契約で冗長に持つことの許容 | **許容する。** アプリ側で常に `Project.customerNo` と同値を書き込んで担保 |
| ② 仮契約（`orderContract` = 0）の扱い | **発注先を持つ。** 受注契約が未決なだけで発注先は決まっている |
| ③ 移行時の値の取得元 | 付け替え前の `project_id` が指すPJの `customer_no` |

### 画面側の現状（alphasys、確認済み）

**契約の追加画面に取引先の入力欄が無い。** 表示はあるが、プロジェクト由来の値を
読み取り専用で出しているだけ。

```
AddContractInfo.tsx

```

**配線は途中まである。** `customerNo` は確認画面・アクションまで持ち回られているが、
`Contract` に保存先が無いため表示にしか使われていない。

### 移行データからも発注先が落ちている（alphasystem 側で確認）

スキーマだけでなく**移行済みデータにも発注先が無い**。移行SQLが次の2つを行って
いるため。

```sql
-- 02_project: 発注プロジェクトを除外
FROM alp_project WHERE order_prj_id IS NULL

-- 03_contract: 発注契約を親（受注）契約の project_id へ付け替え
CASE WHEN ac.order_contract IS NULL THEN ac.project_id
     ELSE aa.project_id END AS project_id
```

旧システムでは発注プロジェクト側が保持していたと見られる発注先が、移行の時点で
捨てられている。**設計の欠落とデータの欠落が同時に起きている。**

→ スキーマを直しても、**移行データの再投入が必要**。

2026-09-30 に決めた**移行手順の一気通貫の再実施**と重なる。**スキーマと移行SQLを
直してから一気通貫を流す**のが無駄がない。

### 旧システムでの発注先の保持場所（確認済み）

- **発注用プロジェクトが用意されており、`alp_project` に保持**していた
- `alp_contract` にも列はあるが、**運用で設定したことがあるだけで宛てにできない**
  （当初「照合用で一致しているはず」としたが、**使えないことが判明**）

→ **`alp_project.customer_no` を使う。**

### 移行での取得ルール（論点③の結論）

**付け替え前の `project_id` が指すプロジェクトの `customer_no` を取る。**

| 契約種別 | 付け替え前の project_id | 取れる取引先 |
| --- | --- | --- |
| 受注契約 | 受注PJ | 受注先 |
| 発注契約 | **発注PJ** | **発注先** |

契約種別で分岐する必要がない。現行の移行SQLは発注契約の `project_id` を親（受注）
契約のものへ付け替えているため、**付け替え前の値で結合する**点だけが要点。

発注PJ自体は移行対象外のまま（`customer_no` だけ引き継ぐ）。

**検証項目**: 発注契約なのに付け替え前の `project_id` が受注PJを指す行が無いか。
あれば発注先が取れないため、件数と内容を見てから扱いを決める。

### 役割分担

- **alphasystem（当セッション）** … 仕様の決定と記録のみ
- **alphadb プロジェクト** … テーブル変更、移行スクリプトの修正を相談・実施
- **alphasys** … 画面の修正（契約の追加・編集での取引先指定、請求一覧の表示）

### 仕様案（論点3点は未決）

**`Contract` に取引先番号を追加し、必須とする。**

| 契約種別 | 入る値 |
| --- | --- |
| 受注契約（`orderContract` が NULL） | 受注先（= `Project.customerNo` と同値） |
| 発注契約（`orderContract` が非NULL） | 発注先（仕入先） |

任意（NULL可）にすると「NULLならプロジェクトから引く」分岐が全参照箇所に残り、
請求一覧・契約一覧・プロジェクト一覧で同じ分岐を書くことになる。今回のバグと
同種の取りこぼしが起きやすいため、必須とする案。

| # | 論点 | 内容 |
| --- | --- | --- |
| ① | 受注契約で冗長に持つことの許容 | `Project.customerNo` と同値を複製するためズレうる。アプリ側で常に同値を書く運用で担保する想定 |
| ② | 仮契約（`orderContract = 0`）も取引先を持つか | 受注契約が未決なだけで発注先は決まっているはず。移行後に `0` が保持されているかの確認も要る |
| ③ | 移行時の値の取得元 | **決定済み。** 付け替え前の `project_id` が指すPJの `customer_no`（上記） |

## 2026-10-08 契約に取引先が無い設計バグ — 個別修正を中断して対応する

### 方針変更

**UI調整・バグ改修・未実装部分の実装（2026-10-07 の優先順位）をいったん中断し、
こちらを先に対応する。**

### 何が起きているか

プロジェクトを**受発注一体化**した。プロジェクトは受注駆動のため
`Project.customerNo` には**受注取引先**が入る。

```
旧: プロジェクトが発注・受注に分かれ、発注PJが対応する受注番号を保持
新: プロジェクトは受注のみ。発注契約は受注PJにぶら下がる
```

一方 `Contract` は `projectId` と `orderContract`（発注契約なら親の受注契約No）を
持つだけで、**取引先番号を持たない**。辿れるのはプロジェクトの受注先だけなので、
**発注契約の相手先（協力会社）を記録する場所が無い**。

### 移行データからも発注先が落ちている

移行SQLは発注プロジェクトを除外し、発注契約を**親（受注）契約の `project_id` へ
付け替えて**いる。

```sql
-- 02_project
FROM alp_project WHERE order_prj_id IS NULL        -- 発注PJを除外

-- 03_contract
CASE WHEN ac.order_contract IS NULL THEN ac.project_id
     ELSE aa.project_id END AS project_id          -- 発注契約を受注PJへ付替え
```

旧システムでは発注プロジェクト側が保持していたと見られる発注先が、
**移行後のデータに残っていない**。**設計の欠落とデータの欠落が同時に起きている。**

### 想定している方式（未確定）

`Contract.customerNo` を**必須**で追加する。

| 契約 | 入る値 |
| --- | --- |
| 受注契約 | プロジェクトと同じ取引先（冗長だが明示） |
| 発注契約 | 発注先（協力会社） |

NULL 可にして「NULL ならプロジェクトから引く」案もあるが、参照元が2つになり
画面もSQLも分岐が増えるため採らない見込み。

**旧システムで発注先がどこにあったかの裏取り待ち**（発注PJの `customer_no` と
見ているが未確認）。確認後に方式を確定する。

### 波及範囲

| 対象 | 内容 |
| --- | --- |
| alphadb | スキーマ変更 + マイグレーション + publish |
| 移行SQL | 発注契約に発注PJの取引先を引き継ぐよう修正 |
| **移行データ** | **再投入が必要**（現データに発注先が無い） |
| alphasys | 契約の追加・編集画面に取引先の指定を追加 |
| 請求 | 発注契約からの請求が発注先を参照するか要確認 |

先に決めた**移行手順の一気通貫の再実施**と重なる。**スキーマと移行SQLを直してから
一気通貫を流す**のが無駄がない。

## 2026-10-09 MFクラウド連動 — CSV から API へ。オンデマンドバッチ方式とする

### 方針

- **CSV連携から API連携へ切り替える**
- 月次データ全体を送受信するため、**オンデマンドバッチ処理**とする
- **起動契機のみ alphasys から与え、バックグラウンドで動作**させる
- 実処理の置き場所は **`alphabatch` か `alphaexapi`**（**未決**）

### 役割分担

- **alphasystem（当セッション）** … 仕様の取り決めと記録のみ
- **alphasys / alphaexapi など** … 共有された仕様に基づく実装

### 現行業務フロー（今回ヒアリングした内容）

既存のロードマップ（2026-07-27）はタスク1〜3を「何をするか」の粒度でしか
書いておらず、以下は**新しく判明した業務の具体**。

#### 取引先情報の連動

- **取引先管理をマスター**とし、MFC債務支払・MFC請求書・MFC会計へ連動したい
- **現行システムでは実現できていない。現在は社名のみでリンク**している

#### 請求書データの連動（現行はCSV）

1. **月初に、前月末時点の契約情報をもとにCSVを作成**
   - 金額欄は `cont_earnings` 列の数字または **0**
   - **既に請求情報が存在する場合は、そのレコード値を使用**
2. CSVをMFC請求書でインポートし、**確定数字を入力**
3. **対象月単位でCSVダウンロード**し、社内システムへインポート

#### 債務支払データの連動（現行はCSV）

ほぼMFC請求書と同様のフロー。**ただしエクスポートが異なる**。

- 経理業務の集計（支払処理）の**明細（支払日）単位の詳細ボタン**から明細CSVを
  ダウンロードし、社内システムへインポート
- **品目が `XXXX_契約名`（XXXX は契約番号）のものを対象**としてインポート
- **営業関連でない支払いが混在した場合は読み飛ばす**
- **同じ費用計上日で XXXX が重複する際は合算する**
- 多くの場合、借方科目は**外注費**と**旅費交通費**

### 既存文書との食い違い（要修正）

ロードマップの**タスク3（請求管理・仕入）は「タスク2の設計・実装を流用」**と
書かれているが、**同型ではない**。

債務支払の取込には、請求書側に無い処理がある。

- 品目名からの契約番号の抽出
- 非営業の支払いの読み飛ばし
- 同一費用計上日での合算

→ 設計を分ける必要がある。

### 論点1: 実行方式 — ✅ `alphaexapi` にそのまま置く（A案で確定）

#### 月次の処理件数

**請求・債務支払とも100件程度**（ヒアリング）。

請求書APIで判明しているレート制限は**一部エンドポイントで1秒3回**。100件を連続で
送っても**約34秒**で、取込を合わせても数分に収まる。現在 `alphaexapi` で動いている
営業メール取り込みは299件を11秒程度で処理しており、**同じプロセスで捌ける規模**。

#### 比較した3案

| 案 | 内容 | 判断 |
| --- | --- | --- |
| **A. `alphaexapi` にそのまま置く** | 既存の `@Cron` + アドバイザリロックの型を使う | **採用。**最小の作業で済む |
| B. ポーラー専用サービスを分離 | `desiredCount=1` の別 ECS サービス | 見送り。処理時間が問題になれば CDK 変更だけで移行できる |
| C. `alphabatch` を新規構築 | SQS + ワーカー | 見送り。件数に対して作業量が大きすぎる |

#### 調査で判明した前提（重要）

- **`alphabatch` はサンプル。** 中身はガス・でんき請求のCSV連携で別システム由来。
  **CDK にインフラが一切無い**（SQS・ワーカーとも未構築）。「既存のバッチ基盤を使う」
  のではなく「新規構築する」ことになる
- **`alphaexapi` には必要な要素が揃っている。** ECS で常駐し、バックグラウンド実行の
  実績がある。複数タスクでの重複実行を防ぐ仕組み（`pg_try_advisory_lock`）も
  2026-09 に実装・動作確認済み
- タスク0 plan は元々 `alphaexapi` 前提で書かれており、**前提の見直しは不要**

#### `alphabatch` の動作環境

**整えたいが優先度は低い。** 今回の MF 連動では使わない。

### 実装前に確認が要ること

**下位プランの「書類種別ごと100リクエスト上限」が、月次件数とちょうど同水準。**
この上限が月あたりか日あたりかで、**100件の送信が1回で頭打ちになる可能性**がある。
契約プランと上限の単位を MF 側に確認する。

アーキテクチャの選択は変わらない（A のまま）が、実装着手前に確定させる。

### 論点2: 取引先連動（検討中）

#### ① 同期の向き — ✅ 決定

**社内システムがマスターで一方向。** MF側の変更は取り込まない。

#### ② 既存データの突合 — 実データで確認（2026-10-09）

MFCからエクスポートした3製品分のデータで裏取りした
（`G:\マイドライブ\社内システム\MFクラウド\顧客管理`）。

**コード体系が判明した。**

| 形式 | 意味 |
| --- | --- |
| **`S` + 10桁ゼロ埋め** | **社内システムの `customer_no`**（例: `S0000000207` → 207） |
| `A` + 10桁連番 | **MF側の自動採番**。社内システムと紐付いていない |

**紐付き状況**

| 製品 | 件数 | S（紐付き） | A（未紐付き） | 空 |
| --- | --- | --- | --- | --- |
| 請求書 | 35 | **23**（ユニーク22） | 0 | **12** |
| 債務支払 | 101 | **77**（ユニーク76） | 24 | 0 |
| **会計** | 88 | **0** | **88** | 0 |

- **会計は1件も紐付いていない。** 全件がMF側の自動採番
- 請求書・債務支払は**大半が `customer_no` で紐付いている**（想定より進んでいた）
- 請求書に**空コードが12件**（「名前のみで連携しているものもある」がこれ）
- 請求書で `S0000000207` が**2行ある**（二重登録の可能性）

**初期マッピングは S コードから機械的に作れる。** 社名での突合が必要なのは、
請求書の空12件・債務支払のA 24件・**会計のA 88件**。会計が最大の山。

#### ③ 同期の契機 — ✅ 決定: 月次バッチに含める

**請求書・債務支払の処理に先立って取引先を登録する。** 都度同期はしない。

都度同期だと、取引先の登録・更新のたびにMFのAPIを叩くため、**MF側が落ちている
ときに社内システムの操作が止まる**（または失敗が溜まる）。月次バッチなら切り離せる。

→ 月次バッチの処理順は **取引先 → 請求書 / 債務支払**。

#### 会計は法人番号で突合する（2026-10-09 決定）

社名突合ではなく**法人番号で紐づける**方針。実データで充足率を確認した。

| 対象 | 充足 |
| --- | --- |
| 会計CSV 法人番号（13桁） | **88件中87件**（空1件） |

| 債務支払CSV マイナンバー/法人番号 | 36件のみ（空55・その他10） |

| 社内（**取引停止を除く**） | **134件中76件（57%）。空58件** |

#### ⚠️ 訂正 — 法人番号だけでは会計88件を賄えない

当初「会計はほぼ全件が機械的に突合できる見込み」と記録したが、**MF側だけを見た
片側の判断だった**。社内側を測ったところ**充足率は31%**しかない。

**一致するのは多くても76件。** 残りは社内側に法人番号が無く、突合できない。

**両側に重複がある。**

| 側 | 重複 |
| --- | --- |
| 社内 `alp_customer` | 76件中ユニーク75 → **1件重複** |
| MF会計CSV | 87件中ユニーク86 → **1件重複** |

同じ法人番号が複数の取引先に入っている組があり、突合が一意に決まらない。件数は
小さいので個別に確認して片付ける。

> インボイス登録番号（`T` + 法人番号）はMF側で88件すべて揃っているため、
> MF側の法人番号が空の1件はそこから復元できる可能性がある。

#### 取引停止を除くと見通しが改善する

**法人番号を持つ76件はすべて現役**（取引停止を除いても76件のまま）。
**空は58件**まで減る。

| 母数 | 全件 | 法人番号あり | 空 |
| --- | --- | --- | --- |
| 全取引先 | 247 | 76 | 171 |

**この連動の前提として、社内 `alp_customer.corporate_number` の登録が要る。**
対象は**現役で空の58件**のうち、**MF会計に出てくる取引先に絞った分**。
取引停止先を埋める必要は無い。

実際の重なり件数は、会計CSVの法人番号86件を使った突合SQLで測る（未実行）。

債務支払の法人番号は充足率が低いため、**未紐付け24件の突合には使えない**。

#### 未紐付け分は手作業で対応する（2026-10-09 決定）

請求書の空12件・債務支払のA 24件は、**MF側で直接コードを入れる手作業**で片付ける。
**紐付け用の画面は作らない。** 従来も手作業で行っており問題ないため。

#### 業務ルール: 法人番号が必要なのは発注先のみ

**基本的に法人番号が必要な取引先は発注先のみ**（2026-10-09 ヒアリング）。
仕入税額控除のために支払先の登録番号が要るという位置づけ。売り先（受注先）の
法人番号は不要。

→ 社内側で法人番号を埋める対象は**発注先に絞られる**。

> ⚠️ **発注先の特定には、契約への取引先追加（2026-10-08 の仕様）が前提になる。**
> 現在のデータでは発注契約の相手先が存在しないため、誰が発注先かを機械的に
> 判別できない。**MF連動の取引先同期は、契約の取引先追加の後**に来る。

#### 会計と債務支払の重なり（実測）

| | 件数 |
| --- | --- |
| 法人番号で両方にある | **33** |
| 会計のみ | **53** |
| 債務支払のみ | 3 |
| （参考）社名で共通 | 47 / 会計88・債務支払100 |

**会計の方が債務支払より広い。** 法人番号は会計86件に対し債務支払36件。社名でも
会計88件中47件しか債務支払に出てこない。

→ **会計の取引先は発注先だけではない。** 経費・その他の支払先など、債務支払を
通さない相手が含まれている。社内システムが関知しない相手がいるため、
**社内がマスターになれない**。

#### ✅ 決定: 会計を連動対象から**一旦**外す

連動先を**請求書と債務支払の2つに絞る**。根拠は以下。

- 会計の取引先は社内システムより広く、社内がマスターになれない相手を含む
- ロードマップの基本方針は「財務会計はMFクラウドに任せる」
- 法人番号が必要なのは発注先で、それは**債務支払**の管轄
- 会計へはMFクラウド内の製品間連携で届く想定

> 「一旦」外す位置づけ。将来的に見直す余地は残す。

#### ✅ 決定: 法人番号は今後すべて設定する

社内 `alp_customer.corporate_number` は**全件に設定していく予定**（運用）。

このため、法人番号の登録対象を「発注先のみ」に絞る必要は無くなる。現状は現役
134件中76件（57%）で空が58件だが、これを埋めていく。

→ 将来的には**法人番号での突合が全取引先に対して使える**ようになる。
ただし**当面は空の取引先が残る**ため、突合は `S` コード（`customer_no`）を主、
法人番号を従とする設計が現実的。

#### 論点2 の状態

| # | 論点 | 状態 |
| --- | --- | --- |
| ① | 同期の向き | ✅ 社内システムがマスターで一方向 |
| ② | 既存データの突合 | ✅ `S` コードで初期マッピング。未紐付けは手作業。会計は対象外 |
| ③ | 同期の契機 | ✅ 月次バッチに含める（請求書・債務支払に先立つ） |

**論点2は決着。** 会計CSVとの突合SQLは不要になった（会計を対象から外したため）。

### 論点3・4: 請求書／債務支払の連動（2026-10-09 ヒアリング）

#### ① 対象契約の抽出条件

**請求一覧の検索月の月末日時点で生きている契約。**

```
contFrom <= 検索月の月末日 <= contTo
```

#### ② 金額の決定ルール

1. **請求情報が既に登録されていれば、請求情報の値を使う**
2. 存在しない場合、売上仕入予定金額 `cont_earnings` を採用

#### ③ 取込時の突合キー

| 連動先 | 日付の突合 | 契約の突合 | 備考 |
| --- | --- | --- | --- |
| MFC請求書 | **売上計上日** = 指定月末 | 品目データの**品名先頭パート** = `contract_no` | |
| MFC債務支払 | **費用計上日** = 指定月末 | 品目データの**品名先頭パート** = `contract_no` | **外注費・旅費交通費を合算** |

#### ④ 再実行時の扱い

**品名の先頭パートを当月のキーとする。** これで同じ月を2回流しても二重作成しない。

#### 実データで確認した規約（2026-10-09）

インポート用CSVサンプル（`G:\マイドライブ\社内システム\MFクラウド\`）で確認。

**品名の書式**

```
6059_ろうきん勘定系基盤更改対応＿角田
^^^^ ^                ^
 |   |                └─ 契約名の区切りは全角アンダースコア「＿」
 |   └─ 区切りは半角アンダースコア「_」
 └─ contract_no
```

**最初の半角 `_` で分割すれば `contract_no` を取り出せる。** 契約名側は全角を
使っているため衝突しない。

**規約の充足率は100%。** 請求書59件・債務支払81件とも `数字_` 始まり。

**CSVの構造**

| | 行形式 | 内訳 |
| --- | --- | --- |
| 請求書 | `請求書` / `品目` | 24 / 59 |
| 債務支払 | `支払依頼` / `明細` | 53 / 81 |

ヘッダ行と明細行が同一CSVに混在する形式。

#### ⚠️ 「外注費」は貸方科目ではなく経費科目

ヒアリングでは「貸方費目=外注費および旅費交通費」とあったが、**インポート用CSVでは
列が分かれている**。

| 列 | 値（サンプル81件） |
| --- | --- |
| 貸方科目 | **買掛金**（全件） |
| **経費科目** | **外注費**（全件） |

→ 合算の判定に使うのは**経費科目**。サンプルに旅費交通費は含まれていない。

#### 取込側（エクスポート）の実データで確認（2026-10-09）

| | 列構成 |
| --- | --- |
| **請求書** | **入出力で同一**（38列）。`売上計上日` `品名` の位置も同じ |
| **債務支払** | **別形式**（29列）。`経費科目` は5列目、`品目` は4列目、`費用計上日` は27列目 |

**読み飛ばしが実在した。**

| 品目 | 件数 | 扱い |
| --- | --- | --- |
| `数字_契約名` | **31** | 取込対象 |
| **`営業支援費`** | **3** | **読み飛ばし**（営業関連でない支払い） |

品名規約で機械的に判別できる。

**経費科目の実態**

| 経費科目 | 件数 | 借方科目 / 貸方科目 |
| --- | --- | --- |
| 外注費 | 30 | 外注費 / 買掛金 |
| **旅費交通費** | **1** | 旅費交通費 / **未払金** |
| **業務委託料** | **3** | 業務委託料 / 買掛金 |

判定に使うのは**経費科目**の列で確定（貸方科目ではない）。

#### 科目と品目を突き合わせた結果 — 仕様と実データは完全に一致

当初「業務委託料が3件あり契約に紐づく支払いに見える」と記録したが**誤り**。
品目と経費科目を別々に集計し、突き合わせていなかった。

**「業務委託料」3件と、読み飛ばし対象の「営業支援費」3件は同じ3件。**

| 経費科目 | 件数 | 品目 | 扱い |
| --- | --- | --- | --- |
| 外注費 | 30 | `数字_契約名` | 取込対象 |
| 旅費交通費 | 1 | `6021_データセンターサーバー構築、運用保守作業＿若山` | **取込対象** |
| 業務委託料 | 3 | **`営業支援費`**（契約番号なし） | **読み飛ばし** |

**ヒアリングの仕様（外注費・旅費交通費を対象、営業関連でないものは読み飛ばし）と
実データは矛盾しない。** 旅費交通費の1件も品目に契約番号があり、同じ契約の外注費と
合算される対象。

#### ✅ 決定: 判定方式は品名規約。経費科目は監視対象（2026-10-09）

**品名が `契約番号_契約名` の形式であるものを取込対象とする。** 経費科目は判定に
使わない。契約番号単位で合算する。

**経費科目は外注費がほとんどで稀に旅費交通費。それ以外が来た場合は、取り込んだ
うえで警告メッセージをログに残す。除外はしない。**

取りこぼしを防ぎつつ、科目の増加に気づける形。除外条件にすると契約に紐づく支払いが
黙って落ち、何も記録しないと仕様の前提が崩れたことに誰も気づかない。

→ 詳細は[仕様書 5.2](design/2026-10-09-MFクラウド連動-仕様.md)

#### （検討時の論点）判定方式

このデータでは**品名規約での判定と科目の列挙は同じ結果**になる。

| 方式 | 内容 |
| --- | --- |
| 列挙 | 外注費・旅費交通費だけを取り込む。新しい科目が増えたら取りこぼす |
| **規約で判定** | 品目が `数字_` 始まりなら科目を問わず取り込む。読み飛ばしは規約外のものだけ |

**規約での判定を推す。** 将来「業務委託料」で契約に紐づく支払いが出てきても自然に
拾える。列挙だとそのたびに設定の追加が要る。

## 2026-10-10 MFクラウド連動 — ジョブ実行状態モデルとPDF保管方針を決定

### ✅ 決定: ジョブ実行状態のモデル

[2026-10-09 仕様](design/2026-10-09-MFクラウド連動-仕様.md) の唯一の未決だった7章が決着。
`alphadb` に `MfJob`（`alp_mf_job`）と `MfJobDetail`（`alp_mf_job_detail`）を追加する。

| 論点 | 決定 |
| --- | --- |
| ジョブ種別の粒度 | **5つに分ける**（取引先同期 / 請求書 送信・取込 / 債務支払 送信・取込） |
| `MfJobDetail` の要否 | **持つ** |
| 履歴の保持期間 | **2年**（24ヶ月より古いジョブを月次バッチ起動時に削除。明細は cascade） |

**種別を5つに分ける理由。** 送信と取込の間に「人がMFCで確定数字を入力する」手作業が
挟まるため、連続した1ジョブにできない。画面からは「月次送信」「月次取込」をまとめて
起動し、内部で種別ごとに `MfJob` を作る。失敗したものだけ後から再実行できる。

**明細を持つ理由。** 「想定外の経費科目で取り込んだ」という警告や、どの契約が失敗したかを
**画面で確認できるようにする**ため。ログだけでは CloudWatch を見に行くことになり、
経理担当者の手には負えない。月100件 × 5種別 × 12ヶ月で年間6,000行程度、量は問題にならない。

二重起動は `unique(jobType, targetMonth)` ではなく **`status = RUNNING` の存在チェック**で
防ぐ（再実行を履歴として残すため）。アドバイザリロックを併用する。

→ 詳細は[仕様書 7章](design/2026-10-09-MFクラウド連動-仕様.md)

### ✅ 決定: 書類（PDF）の保管方針 — 方針のみ記録

請求書ドキュメントPDFのやり取りについては、**方針のみ記録し連動方式は未検討とする。**

| --- | --- | --- |
| **契約書** | **社内システム** | Google Drive |
| **請求書** | **MFクラウド** | BOX |

**ただし過去データはすべて社内システムがベース。** MFクラウドに請求書のベースを移すのは、
API連動の開始以降に発行するものから。

→ 詳細は[仕様書 8章](design/2026-10-09-MFクラウド連動-仕様.md)

### これでMFクラウド連動の仕様は一通り確定

残る未決は「請求書PDFの受け渡し方式」と「MFのリクエスト上限の単位（月か日か、MFへ確認）」の2件。
実装は alphadb / alphaexapi / alphasys の各セッションで進める。

## 2026-10-15 複数プロジェクトセッション間の連携方法を決定

### きっかけ

alphasystem（全体調整）→ alphadb/alphaexapi/alphasys等（詳細設計）とセッションを分けて
作業する現行方式では、プロジェクト間の情報連携がうまくいかず、同じ背景説明を複数セッションに
手入力する手間がかかり時間がかかりすぎることがあった。一方で、各プロジェクトに閉じた
やり取りはそのプロジェクトの会話記録として残したい、という要件がある。

### 検討した案と却下理由

- **alphasystemをハブにし、Agentツールのサブエージェントで各リポジトリに作業を投げる案**
  → 却下。サブエージェントの実行はalphasystem側セッションの一部でしかなく、個別プロジェクトの
  `conversations.md`には記録されない。閉じた話を個別プロジェクトに残したいという要件と合わない。

### ✅ 決定: セッションは今まで通りプロジェクトごとに分け、`SendMessage`で直接つなぐ

- プロジェクトごとにセッションを分ける現行の構成（alphasystemで設計 → alphadb/alphaexapi/
  alphasys等で詳細設計）は維持する。これにより各セッションのStopフックがそれぞれの
  プロジェクトの`conversations.md`に正しく記録される。
- セッション間の情報連携は、人間が間に入って転記するのではなく、`ListAgents`/`SendMessage`で
  動作中の他プロジェクトのセッションに直接メッセージを送り、文脈の受け渡し・結果の受け取りを行う。
- Agentツールのサブエージェントは、記録を残す必要のない閉じた調査・軽作業（他リポジトリの
  該当コードを探して読むだけ、等）に限定して使う。設計判断や承認が絡むやり取りは、
  必ずそのプロジェクト自身のセッションで行う。

### ✅ 決定: 各プロジェクトのCLAUDE.mdに一文＋本記録へのリンクを追記して周知する

- この運用ルールは各プロジェクトのセッション開始時に自動で目に入らないと埋もれるため、
  各プロジェクト自身の`CLAUDE.md`（セッション開始時に必ず読み込まれる）に短い一文と
  本記録へのリンクを追記する方式を採用した。
- alphasystem自身の`CLAUDE.md`には「セッション間の連携ルール」節として追記済み
  （[CLAUDE.md](../CLAUDE.md)参照）。
- **alphasystem以外（alphadb/alphaexapi/alphasys/alphasyscdk/alphacdk）のCLAUDE.mdへの
  追記は、ユーザー自身が転記する。**（別リポジトリのためこのセッションからは編集できない）

## 2026-10-16 CSV経路復活の根本理由と優先度原則を仕様書に明記(全プロジェクト共通認識化)

上記2026-10-16のCSV経路決定時点では、「現行システムの機能を移行したい」という動機のみを記録しており、**復活の直接のきっかけが債務支払(PAYABLE)の支払依頼作成APIが存在しないことである**という事実を仕様書に明記していなかった。この結果、alphaexapiセッションでCSV経路の実装着手順を検討した際、根本理由を踏まえずに「請求書側から着手し、債務支払側は後回し」という順序を一度提案してしまい、ユーザーから複数回(2回目)の指摘を受けて初めて誤りだと判明する事態が起きた。

### ✅ 決定: 以下を仕様書2.4章に明記し、全プロジェクトの共通認識とする

- **CSV経路復活の直接のきっかけは、債務支払の支払依頼(`invoice_report`)をMF APIで作成できないこと**(`invoice_reports`/`general_reports`はGET専用、作成APIが存在しないことを実機のOpenAPI仕様で確認済み)。債務支払の送信は、API完全移行後もCSV経路(MFクラウド債務支払の「支払依頼」画面でのCSVインポート)への依存が避けられない。
- 請求書側は送受信ともにAPIのみで完結し、CSV経路が無くても業務上支障は無い。請求書側にもCSV経路を用意するのは、現行システムとの機能パリティのための付随的な理由にすぎない。
- **CSV経路に関する作業の優先度は、請求書側を後回しにすることはあっても、債務支払側を後回しにしてはならない。** 計画・設計の完成度等、着手順の都合だけで債務支払CSVを後回しにする判断は、本仕様の前提と矛盾する。

この原則は、プロジェクトをまたいだ共通認識として扱うこと(各セッションがCSV経路の作業順序を検討する際は、都度この経緯を踏まえること)。

### ✅ 決定: ジョブ実行履歴はAPI経路と統合管理する

- CSV経路で取り込んだ分も、7章の`MfJob`/`MfJobDetail`に`sourceType`(API/CSV)等を
  追加して一元管理する(API経路単独案は不採用)。どちらの経路で処理したかに関わらず
  同じ画面・同じ監査証跡で履歴を追えるようにする。
- 7.4の二重起動防止も両経路で共通のアドバイザリロックを使う方針とし、月次バッチ実行中の
  手動アップロードとの競合を防ぐ。

- **配置先**: alphasystem リポジトリ内（コミット対象）。別PCで clone しても同じ動作になることを優先。ユーザー設定（~/.claude）や settings.local.json はこのPC限定になるため不採用。
- **実装上の学び**: `set -o pipefail` 下で `locale -a | grep -q` を使うと、grep -q が先に終了して locale -a が SIGPIPE で非0になり、条件分岐が常に偽になる。`grep -q` をやめて `grep ... >/dev/null` にして解決（UTF-8 ロケール未設定だと日本語メッセージの切り詰めが文字の途中で壊れる）。
- **有効化の注意**: 設定ファイルの監視はセッション開始時に存在した設定ファイルのみ対象のため、このPRをマージ・取り込んだ直後のセッションではフックは発火しない。以後は自動。有効化手順は環境で異なる（2026-10-19 に訂正）:
  - CLI: `/hooks` を一度開く（設定再読込）か、`/exit` で終了して `claude` を再実行。
  - VS Code 拡張: `/exit` は無い。コマンドパレットで `Developer: Reload Window` を実行してから、Sessions アイコンの新規作成または `Claude Code: Open in New Tab`（Cmd+Shift+Esc）で新しい会話を始める。読み込み状態は入力欄 `/` → Customize → Hooks で確認できる。
- **確認済み**: パイプテスト（`echo '{}' | .claude/hooks/project-status.sh`）で9プロジェクト分の表が出力されること、`jq` でフック定義のスキーマ妥当性を確認。
- **VS Code 拡張での実機確認（2026-10-19 11:10）**: `Developer: Reload Window` 後に始めた新規会話で SessionStart フックが発火し、初回応答の冒頭に表が表示されることを確認した（セッション記録 `~/.claude/projects/-Users-yohira-git-alphasystem/<session-id>.jsonl` に `SessionStart:startup hook success: 以下は alphasystem ...` が記録されている）。一方、フック追加作業を行っていた直前のセッション（10:37 開始）には記録が無く、「開始時に存在した設定のみ読む」仕様どおり。

## 2026-10-19 セッション開始時の状況一覧フックの Windows 対応（調査結果・提案中、承認待ち）

- **経緯**: 上記フック導入後、「Windows 上でも対応できるか」との質問。実機は無いため机上で確認した。
- **調査結果**: Git for Windows（Git Bash）があれば動かせる。Claude Code のフックは Windows では Git Bash があれば bash、無ければ PowerShell で実行されるため、bash 専用の本スクリプトは Git Bash が前提条件。WSL 上は Linux そのものなので手当て不要。
- **現状のままだと起きる問題（3点）**:
  1. `.gitattributes` が無く、Windows 側で `core.autocrlf=true` だと `.sh` が CRLF で checkout され bash が失敗する。`*.sh text eol=lf` の追加が必要（最重要）。
  2. Git for Windows の `git rev-parse --show-toplevel` は `C:/...` 形式、スクリプト内の `pwd -P` は `/c/...` 形式を返すため比較が一致せず、alphabsmail 行の「alphasystem内」判定がずれる。比較前の正規化が必要。
  3. `CLAUDE_PROJECT_DIR` がバックスラッシュ区切りで渡る。Git Bash は概ね解釈するが、`cygpath` がある環境では POSIX 形式へ変換する保険を入れたい。
- **問題にならない点**: `locale`/`sed -E`/`date`/`wc`/`tr`/`grep` は Git Bash に揃っている。配下リポジトリの相対パスは Windows 側も `~/git` 直下に clone してあれば同じ構成で解決できる。
- **提案（未承認）**: 上記3点を PR #76 に追加修正として入れる（`.gitattributes` 新規追加＋`project-status.sh` のパス正規化数行。Mac 側の挙動は不変）。Windows 実機確認は、Windows 側で `/hooks` を一度開いた後に新しいセッションを始めて表が出るかを見てもらう。
- **見送り推奨（未決）**: Git Bash 無し環境向けの PowerShell 版スクリプトは二重保守になるため今回は作らない方針を提案。ユーザーの判断待ち。

## 2026-10-22 4_7_1 社員情報（本人用の変更依頼）の確定方式・状態遷移・DC確認方法を決定
