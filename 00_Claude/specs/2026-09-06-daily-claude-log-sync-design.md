# Claude Code 会話まとめの Daily ページ反映（設計）

作成日: 2026-09-06

## 1. 目的

複数の VSCode プロジェクトで行っている Claude Code との会話の結論（各リポジトリの `conversations.md`）を、
Obsidian Vault の Daily ノート（`01_Daily/YYYY-MM-DD.md`）へ自動的に集約する。

各セッションは互いを認識できないが、**全セッションが同じ Daily ファイルを共有し、
終了のたびに全プロジェクトを走査して該当ブロックを作り直す**ことで、結果としてセッション間が連動する。

## 2. 前提（調査で確認済みの事実）

- グローバル CLAUDE.md のルールにより、各リポジトリに `conversations.md` が蓄積されている。
- **配置はリポジトリ直下とは限らない。**全リモートブランチを横断調査した結果、次の 3 パターンが存在する。

  | リポジトリ | パス |
  | - | - |
  | alphacdk / coopinf / coopcdebatch / coopbatch | `conversations.md` |
  | alphasystem | `docs/conversations.md` |
  | alphasystem | `alphabsmail/docs/conversations.md`（1 リポジトリに 2 ファイル） |

- 見出しは 4 パターンが混在する。
  - `## 2026-07-22 CSVバッチ処理のログ出力見直し（提案）`（空白区切り）
  - `## 2026-08-20: gas_bill.option_fee_code_1 埋め戻し — prd適用結果の記録`（コロン区切り）
  - `## 2026-08-12 — 営業メールのやりとりの可視化（brainstorming 開始）`（em ダッシュ区切り）
  - `## 2026-08-28〜31 ステージング環境の作り直しと、そこで見つかった10件の不具合`（日付範囲。実データに 2 件）
  - `## 経営層向け説明資料（PowerPoint）の作成`（日付なし。alphabsmail では 11 セクション中 4 件）
- 本文はおおむね日付昇順で末尾に追記されている。
- `conversations.md` は git 追跡下にあり GitHub（`alphacmc/*`）へ push 済み。ただし更新は
  feature ブランチ上に載ることが多く、デフォルトブランチだけを見ると当日分を取りこぼす。
- 対象プロジェクト一覧は `~/git/alphasystem/CLAUDE.md` と `~/git/coop/CLAUDE.md` のテーブルから機械的に取得できる（17 件）。
  - うちこの PC に clone 済みは 13 件、未 clone は coopcdeweb / coopcdeinput / coopcdealert。
  - `alphabsmail` は相対フォルダーが `./alphabsmail` で独立リポジトリではない。
- 13 リポジトリの並列 `git fetch` は実測 3.0 秒。
- Claude Code の SessionEnd hook はインストール済みバイナリで対応を確認済み。
- `~/.claude` は git 管理外。Vault は git 管理下（obsidian-git が main を直接同期）。

## 3. 構成要素

| # | 実体 | 役割 |
| - | - | - |
| A | `00_Claude/scripts/claude_daily_log.py`（Vault 内・git 管理） | 本体。python3 標準ライブラリのみ |
| B | `~/.claude/settings.json` の SessionEnd hook | 全プロジェクト共通の自動起動 |
| C | `~/.claude/commands/daily-sync.md` | 手動実行用スラッシュコマンド |

スクリプトを Vault 内に置く理由: git 管理され、obsidian-git 経由で他 PC にも同じツールが同期されるため。

### サブコマンド

- `fetch` … 未 clone プロジェクトを `~/git/` へ clone し、全対象リポジトリを並列 `git fetch --prune`（ネットワーク要、約 3 秒）
- `sync` … ローカルのみ走査して Vault を更新（ネットワーク不要、1 秒未満）

## 4. データフロー

0. **対象日の決定**
   既定はローカル時刻（JST）の当日。`--date YYYY-MM-DD` で明示指定でき、過去日の再生成にも使える。
1. **プロジェクト一覧の決定**
   `~/git/alphasystem/CLAUDE.md` と `~/git/coop/CLAUDE.md` の Markdown テーブルをパースし、
   相対フォルダー列が `../` で始まる行のみ独立リポジトリとして採用する（`./` 始まりは配下ディレクトリなので除外）。
2. **conversations.md の探索**（リポジトリごと・任意の深さ）
   - リモート: `refs/remotes/origin/*` の各ブランチを `git ls-tree -r --name-only` で走査し、
     ベース名が `conversations.md` のパスをすべて対象にする。
   - ローカル: `git ls-files` と `git ls-files --others --exclude-standard`（未追跡分）を同様に走査する。
   - `node_modules/` `dist/` `build/` `.next/` `vendor/` 配下は除外する。
3. **ソース識別子の決定**
   パスのディレクトリ部分から `docs` セグメントを取り除き、残りをリポジトリ名に連結する。
   - `conversations.md` → `coopinf`
   - `docs/conversations.md` → `alphasystem`
   - `alphabsmail/docs/conversations.md` → `alphasystem/alphabsmail`
   ファイル単位で独立したプロジェクトとして扱い、Daily の行もミラーノートも分ける。
4. **収集**（ソースごと）
   - ベース: リモート追跡ブランチの内容（＝GitHub の内容。他 PC の作業を含む）
   - 上書き: ローカル作業ツリーの内容（未 commit 分。同一キーならこちらを優先）
   - 同一 blob SHA は 1 回だけ解析する。
5. **抽出**
   正規表現 `^##\s+(\d{4}-\d{2}-\d{2})\s*(?:[:：\-—–]\s*)?(.+)$` で見出しを認識し（空白 / コロン / em ダッシュ区切りに対応）、
   日付を持つセクションを**全て**次の `## ` 見出しの直前まで本文ごと切り出す（`collect_entries` は
   対象日で絞り込まない。`target_date` を省略すると全期間を返す）。日付での絞り込みは
   この後段（cli 側）で「対象日のもの」「ソースごとの最新1件」の2通りに分けて行う
   （ミラー出力は絞り込まず全件を渡す）。
   日付範囲の見出し（`## 2026-08-28〜31 …` / `## 2026-08-31〜09-01 …`）は**終了日**のセクションとして扱い、
   タイトルからは範囲表記を取り除く。終了日の年・月は省略されていれば開始日から補い、
   補った結果が開始日より前になる場合は翌年とみなす（例: `2026-12-30〜01-02` → `2027-01-02`）。
   終了日が不正な日付の場合は開始日を採用する。
   日付を持たない `## ` 見出しはスキップし、「日付なし見出し N 件（ファイルパス）」を警告としてログと
   `/daily-sync` の報告に出す。日付の推測（直前見出しからの継承、git blame 等）は行わない。
   見出しの認識は ```` ``` ```` / `~~~` のフェンスコードブロックを認識し、フェンス内の
   `## ` 始まりの行（コメント中の見出し例示など）は見出しとして扱わない。開始フェンスの
   記号種別・長さ・情報文字列（```` ```python ```` 等）を判定し、同じ記号かつ同じ長さ以上の
   閉じフェンスが現れるまでフェンス内とみなす。
6. **重複排除**
   キーは `(ソース識別子, 日付, サニタイズ後のタイトル)`。タイトルはまず正規化（前後の空白と
   末尾コロンの除去）してから、Obsidian の見出しリンクを壊す文字（`#` `|` `[` `]`）を全角に
   置換するサニタイズを適用し、そのサニタイズ後の文字列をキーにする（サニタイズ前のタイトルで
   重複排除すると、サニタイズ後に同じ文字列へ収束する表記ゆれが別々のエントリとして生き残り、
   ミラー側で衝突する）。
   優先順位はローカル作業ツリー > コミット日時の新しいブランチ。それでも同点の場合
   （同一ファイル内に同日・同タイトルのセクションが複数あるなど）は、
   **ファイル内で後に出現した方**を残す（先に出た方を無条件に残す実装では、後のセクションの
   本文が理由も分からず消えてしまうため）。
7. **ミラー出力**
   `00_Claude/projects/<ソース識別子のスラッシュを - に置換>.md` に、未収録のセクションを本文ごと反映する。
   （例: `alphasystem/alphabsmail` → `00_Claude/projects/alphasystem-alphabsmail.md`）
   ファイルが無ければ `# <ソース識別子> 作業ログ` を先頭に付けて新規作成する。
   見出しは `## YYYY-MM-DD タイトル` 形式に正規化する（Daily からの見出しリンクを一意にするため）。
   既に同じキーが収録済みで本文だけが変化している場合（同じ日のうちに追記された場合）は、
   該当セクションの範囲だけを新しい本文で置換する。
   **収録は全履歴を対象にし、日付の昇順（チェックロジカル順）を保つ。** 新規セクションは、
   既存セクションの中で自分より新しい日付を持つ最初のものの直前に挿入する
   （見つからなければ末尾に追記）。同じ日付の既存セクションがあれば、その後ろに挿入する
   （＝同日内では検出順）。これにより、例えば「今日の分しか無いミラーファイル」に対して
   過去日分をまとめて取り込む（バックフィル）実行をしても、過去分は今日の分より前（ファイル内で上）
   に収まる。
   Obsidian の見出しリンクを壊さないため、タイトル中の `#` `|` `[` `]` は全角に置換してから見出しに書く。
   ミラーノートも Daily と同様に、手書きで加筆された箇所（管理対象セクション外）は変更しない。
8. **Daily 出力**
   `01_Daily/YYYY-MM-DD.md` の管理ブロックのみを毎回再生成する。対象日のエントリ（この日の作業）と、
   対象日が実際の今日と一致する場合に限りソースごとの最新1件（各プロジェクトの最新）を出力する。

## 5. Daily の出力仕様

管理ブロックの中身は**プロジェクトごとに1行のリストだけ**。日別のサブセクションは持たない。

```markdown
## Claude作業ログ
<!-- claude-log:start -->
- **alphasystem** — 2026-09-03 [[00_Claude/projects/alphasystem#2026-09-03 タイトル|タイトル]]
- **alphasystem/alphabsmail** — 2026-08-12 [[…|…]]
- **alphadb** — 記録なし

- **coop** — 記録なし
- **coopinf** — 2026-09-06 [[…|…]]
<!-- claude-log:end -->
```

- 各行は、そのプロジェクト（ソース）の**対象日以前で最新の記録**を指す（as-of 表示）。
  朝は前日以前の最新が並び、その日のセッションで記録ができれば当日日付に変わる。
- `--date` で過去日を再生成しても、その日より後の記録は出さない。
- 並び順は alpha グループ → 空行 → coop グループ → 空行 → その他。各グループの先頭は
  傘プロジェクト（`alphasystem` / `coop`）で固定し、続いてそのサブソース（id 昇順）、
  記録のあるプロジェクト（日付降順・同日は id 昇順）、記録なし（名前昇順）。
- 記録が 1 件も無い場合のみ `- （記録がありません）` の 1 行。
- 更新対象は `<!-- claude-log:start -->` と `<!-- claude-log:end -->` の間だけ。手書き部分は変更しない。
- **Daily ノートが存在しない日は何も作らない**（利用者が毎朝テンプレートから作成する運用を尊重し、
  `daily_missing` として報告する）。
- Daily ノートは存在するがマーカーが無い場合は、ファイル末尾に `## Claude作業ログ` ごと追加する。
- マーカーが片方だけ / 順序が逆 / 重複している場合は、ファイルを書き換えずに `DailyMarkerError` を送出し、
  cli 側で警告として報告する（手書き内容の消失を防ぐため）。

## 6. hook / コマンドの挙動

- SessionEnd hook は `sync` をバックグラウンドで起動し、hook 自体は即座に exit 0 する（セッション終了を遅らせない）。
- 前回 `fetch` **成功**から 30 分以上経過している場合に限り、同じバックグラウンド処理内で `fetch` を先に実行する。
  最終実行時刻は `~/.claude/cache/claude_daily_log.fetch_stamp` に保持する。fetch/clone が
  1件も成功しなかった場合（オフライン等）はこのスタンプを更新しない。成功したかのように
  スタンプだけ進めてしまうと、次回セッション終了時まで 30 分間リトライがブロックされ、
  オフラインの間ずっと同期が止まったままになるため。
- `/daily-sync` は `fetch` と `sync` を続けて実行し、結果（更新されたリポジトリ数・追加行数）を報告する。
- `--date` は `datetime.date.fromisoformat` で検証する。不正な値（書式違反・
  パストラバーサルを狙った値など）が渡された場合は、警告を出し、何も書き込まずに exit 0 する。

## 7. 異常系

- Vault が存在しない、書き込み権限が無い、git コマンド失敗、オフライン → 該当分のみスキップし、常に exit 0。
  - `fetch` の失敗は `sync` の実行に影響しない。fetch は独立した try/except で囲んであり、
    fetch が例外を送出しても警告として記録したうえで必ず sync まで実行する。
- 同時実行は多重起動防止用のロックファイル（`~/.claude/cache/claude_daily_log.lock`）で排他する。
  - POSIX（macOS/Linux）では `fcntl.flock` を使う。
  - fcntl が無い環境（Windows）では `O_CREAT|O_EXCL` によるロックファイル方式にフォールバックする。
    `import fcntl` はガード付き（`try/except ImportError`）なので、Windows でもモジュールの
    読み込み自体は失敗しない。ただし Windows 実機での動作は自動テストで検証していない
    （テストスイートは POSIX 上でのみ動く。フォールバックのロジック自体は `cli.fcntl = None`
    に差し替えたユニットテストで検証している）。
  - ロックが競合した場合は短い間隔で数回（合計 約2秒）リトライしてから諦める。ほぼ同時に
    終了した2セッションのうち後者が即座に諦めてしまうと、その分のエントリが翌日まで
    取りこぼされる可能性があるため。
  - 取得できなければ静かに終了コード 0 で終わる。Daily は毎回全再生成なので、取りこぼしは
    次回実行で回復する。
  - ロック取得の失敗理由は、ファイルシステムエラー（ディスクフル・権限不足等）とロック競合
    （他プロセスが実行中）とをログ上で区別する。
- 未 clone リポジトリの clone に失敗した場合は警告のみ記録し、他リポジトリの処理を継続する。
- ファイル入出力は UTF-8 固定（BOM なし・LF）。Claudian の Write が UTF-16 で書く問題を避けるため、生成・追記は本スクリプトから行う。
  Daily・ミラーへの書き込みは、同じディレクトリへの一時ファイル書き込み＋`os.replace()` に
  よるアトミック置き換えで行う（SessionEnd hook 実行中の強制終了で手書きファイルが
  空・中途半端な状態になることを防ぐため）。
- 動作ログは `~/.claude/logs/claude_daily_log.log` に追記し、1 MB を超えたら 1 世代ローテートする。
- vault リポジトリ直下に `.gitattributes`（`* text=auto eol=lf`）を置き、Windows 側の
  `core.autocrlf=true` によって LF 書き込みが CRLF へ巻き戻され、obsidian-git 経由で
  全文差分が延々発生する事態を防ぐ。

## 8. テスト

python3 標準の unittest で実装し、ネットワークには接続しない。
一時ディレクトリにダミーの git リポジトリ・CLAUDE.md・Vault を構築して検証する。

- CLAUDE.md テーブルのパース（`../` 採用 / `./` 除外 / 見出し行除外）
- 任意の深さの `conversations.md` の探索（直下 / `docs/` 配下 / `<サブ>/docs/` 配下、`node_modules/` 除外）
- ソース識別子の生成（`docs` セグメント除去、1 リポジトリ 2 ファイルが別プロジェクトとして分かれること）
- 見出し 3 形式（空白 / コロン / em ダッシュ区切り）の抽出
- 日付範囲見出しが終了日に割り当てられること（日のみ省略 / 月またぎ / 年またぎ / 不正な終了日）
- 日付なし `## ` 見出しがスキップされ、警告として件数が報告されること
- セクション本文が次の `## ` 直前まで正しく切り出されること
- Daily 新規作成
- 既存 Daily の手書き部分が保持されること
- マーカーが無い既存 Daily への追加
- 同じ入力で 2 回実行して差分が出ないこと（冪等性）
- 同じキーのセクション本文が増えた場合に、ミラー側の該当セクションだけが置換されること
- タイトルに `#` `|` `[` `]` を含む場合に見出しがサニタイズされ、Daily のリンクが壊れないこと
- `--date` 指定で過去日を再生成できること
- リモートブランチとローカル作業ツリーで内容が異なる場合にローカルが優先されること
- 該当 0 件の日にマーカーブロックが空になること
- `conversations.md` を持たないリポジトリのスキップ
- 未 clone・git 失敗時に exit 0 で終了すること
- フェンスコードブロック（```` ``` ````/`~~~`、情報文字列付き、ネストした短いフェンス）内の
  `## ` 始まりの行が見出しとして誤検出されないこと
- 走査そのものが失敗した場合（`CLAUDE.md` 皆無 / 対象プロジェクト未 clone / 全プロジェクトで
  収集失敗）に Daily ノートが一切書き換えられないこと。走査に成功し対象日 0 件の場合との
  区別
- Daily・ミラーへの書き込み中に `os.replace()` が失敗しても、既存ファイルが空・破損状態に
  ならないこと（一時ファイルも残らないこと）
- `fetch` が例外を送出しても `sync` が実行されること
- fetch/clone が1件も成功しなかった場合に fetch スタンプが更新されないこと。1件でも
  成功すれば更新されること
- ロック競合時に数回リトライしてから諦めること。ファイルシステムエラーとロック競合とで
  ログメッセージが異なること
- fcntl が無い環境（`cli.fcntl = None` に差し替え）でもロックによる相互排他が機能すること
- `import fcntl` がガード付きであること（トップレベルの無防備な import が無いこと）
- マーカーに前後の空白が付いていても正常なマーカーとして認識され、二重にブロックが
  追記されないこと
- マーカーの順序違反・欠落・重複それぞれで、エラーメッセージが状態を正しく名指しすること
- 同一キーで重複排除する際、rank が同点なら order の大きい方（ファイル内で後）が残ること
- サニタイズ後に同じ文字列になるタイトルが重複排除で1件に統合されること
- 不正な `--date`（書式違反・パストラバーサル狙い）が警告のみで exit 0 になり、何も
  書き込まれないこと
- テストは実ユーザーの `~/.claude`（ロック・ログ・スタンプ）を一切触らないこと
  （`cli.LOCK_PATH` / `cli.LOG_PATH` / `cli.STAMP_PATH` を一時ディレクトリへ差し替える）
- `collect_entries` の `target_date` を省略（`None`）すると全期間のセクションが返ること
  （文字列を渡した場合は従来通りその日付だけに絞り込まれること）
- ミラーへ過去日のセクションを追加すると、既存の新しい日付のセクションより前（ファイル内で上）に
  挿入されること。同じ日付の既存セクションがある場合はその後ろに挿入されること。
  複数セクションをまとめて（日付順不同で）渡しても、結果はチェックロジカル順になること
- 上記のバックフィル後に同じ入力で再実行しても差分が出ないこと（冪等性・バイト同一）
- Daily の「この日の作業」サブセクションは対象日 0 件でも省略されず、固定の1行
  （`- （この日の記録はありません）`）になること
- 「各プロジェクトの最新」サブセクションは `--date` で過去日を指定した実行では一切出力
  されないこと。対象日が実際の今日と一致する場合にのみ出力されること
- 「各プロジェクトの最新」は、記録があるソースが日付降順・同日はソース識別子昇順で先に並び、
  記録が無いプロジェクト（`- **<名前>** — 記録なし`）はプロジェクト名昇順で後に続くこと
- `alphasystem/alphabsmail` のように、プロジェクト名の配下にある別ソースが記録を持つ場合、
  プロジェクト自体は「記録なし」にならないこと（ソース識別子の先頭セグメントで判定）
- 「各プロジェクトの最新」を出力する場合、対象日のエントリが0件でも Daily ノートが新規作成
  されること（最新サブセクションには常に意味のある内容があるため）
- 両サブセクションがシステム単位（`alpha` 始まり / `coop` 始まり / それ以外）でグループ化
  されること。具体的には:
  - alpha グループ内で `alphasystem`（傘プロジェクト）が記録の有無に関わらず常に先頭に来て、
    続けてサブソース（`alphasystem/...`、id 昇順）、残りの記録あり（日付降順・同日は id 昇順）、
    記録なし（名前昇順）の順になること
  - coop グループも同じ4段階（傘プロジェクトは `coop`）で並ぶこと
  - alpha グループと coop グループの間に空行が1行だけ入ること
  - 一方のグループに該当項目が1件も無い場合は、そのグループも区切りの空行も丸ごと省略され、
    余計な空行が残らないこと
  - 傘プロジェクト自身の記録が無い場合でも `- **alphasystem** — 記録なし` として先頭に出ること
  - `alpha`/`coop` のどちらにも一致しないプロジェクトは3つ目のグループとして
    （2つ目の空行の後に）出力され、静かに消えないこと

## 9. スコープ外

- conversations.md 自体の書式統一やリライト
- Vault の自動 commit / push（obsidian-git に委ねる）
